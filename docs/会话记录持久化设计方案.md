# 会话记录持久化设计方案

> 版本：v0.3（设计稿）｜ 日期：2026-10-23 ｜ 状态：待实现（供评审）｜ 关联：`core/qa_router/router.py::_persist_session`，架构依据 `docs/访问模型与会话架构决策.md` §2
>
> 版本演进：v0.1 初稿 → v0.2 取消用户打分 → v0.3 补齐**数据结构设计（Redis 元素 + MySQL `rag_turn` DDL/ORM）**、**写入流程细则**、**查询与保留策略**，并明确与《上下文装配与压缩设计方案》的边界、为 RAGAS 预留接入位置。

---

## 1. 背景与问题

- 当前 `QARouter.answer` / `answer_stream` 在生成后调用 `_persist_session(...)`，但该方法为 **no-op**（仅 `logger.debug('会话记录持久化未实现，跳过')`）。
- 结果：每一轮问答的 `query / answer / intent / 召回片段 / 使用模型 / token 消耗 / 耗时` 都没有落库，无法支撑：
  - **审计与合规**（谁在何时问了什么、得到了什么）；
  - **质量分析**（后续 RAGAS 评测需要 question/answer/contexts 三元组）；
  - **多轮上下文回看**（现有 `core/session` 已支持会话级 content，但 QA 明细未结构化写入）；
  - **运营统计**（命中来源分布、FAQ 命中率、RAG 占比）。

## 2. 目标与非目标

**目标**
1. 持久化每轮 QA 明细，结构可查询、可追溯、可导出给评测管道。
2. **复用既有会话存储体系**（`store/session_store.py` + MySQL `rag_session` + Redis 会话原文 LIST），不新建平行的会话存储。
3. 写入 **不阻塞生成主链路**（异步落库），失败**降级**（记日志、不抛错、不影响回答）。
4. 保持 `(user, session)` 隔离边界，租户维度只做统计不参与隔离。

**非目标（明确不做，避免与相邻文档重叠）**
- 不做 prompt 装配、不做记忆/历史的裁剪取舍——那是《上下文装配与压缩设计方案》的事。
- 不做用户打分，不做任何质量评估计算——那是 RAGAS 评测管道的事（见 §9）。
- 不改 `session_id` 生成策略、不改记忆 compaction 触发规则——那是《访问模型与会话架构决策》§2 的事。

## 4. 设计原则（对齐工程约定）

- **数据访问只落在 `store/`**：落库委托 `store/session_store.py` 与新增 DAO，`core/qa_router` 不直接写 SQL。
- **Redis key/TTL 集中**在 `store/redis_keys.py`，新增 key 不硬编码。
- **schema 由 ORM 生成**（`scripts/gen_schema.py` 输出 `scripts/schema.sql`），新增表走 `store/orm_models/`，**禁止手改 schema.sql**。
- **隔离**：`user_id` 取自网关 `X-User-Id`（全局唯一，跨租户不重复），会话由服务端 `uuid.uuid4().hex` 生成；`tenant_id` 仅作统计列，不作为查询隔离条件。

## 5. 数据结构设计

### 5.1 现状盘点（代码实证）

| 存储 | 位置 | 现状 |
|---|---|---|
| 对话原文 | Redis LIST，键 `u:{user_id}:sess:{session_id}` | 元素 `{role, content, ts}`，TTL 取 `config.REDIS_TTL_SESSION_CONTENT`（30d） |
| 会话记忆 | Redis STRING，键 `u:{user_id}:sess:{session_id}:memory` | `{summary, facts, updated_at}`，TTL 取 `config.REDIS_TTL_MEMORY` |
| 会话索引 | Redis SET，键 `u:{user_id}:sessions` | 热路径辅助，列表以 MySQL 为准 |
| 会话注册表 | MySQL `rag_session` | `user_id / session_id / title / preview / memory_summary / turn_count / 时间`；UK `(user_id, session_id)` |

> **与架构决策文档的一处出入**：`docs/访问模型与会话架构决策.md` §2.2 写的键是 `t:{tenant}:u:{user}:sess:{sid}`，**代码实际为 `u:{user}:sess:{sid}`**（见 `store/session_store.py::_conv_key`，未走 `tenant_key`）。本设计按代码现状编写；若后续需要把租户段加回 key，应同步改 `store/redis_keys.py` 并做存量 key 迁移，不在本轮做。

### 5.2 Redis：会话原文元素扩展

保持「一条消息一个 LIST 元素」的既有约定，一轮问答产生 `user` + `assistant` 两条。**QA 明细只挂在 `assistant` 元素上**（检索/模型/耗时都是产出侧属性），`user` 元素保持轻量，兼容历史数据。

```jsonc
// user 元素（结构不变）
{ "role": "user", "content": "年假怎么算？", "ts": 1760000000, "turn_id": "a1b2c3..." }

// assistant 元素（新增字段，旧元素缺字段按缺省处理）
{
  "role": "assistant",
  "content": "根据《员工手册》…",
  "ts": 1760000003,
  "turn_id": "a1b2c3...",           // 同一轮两条消息共享，用于 Redis↔MySQL 对账
  "tenant_id": 1,                   // 仅统计用
  "intent": "专业咨询",
  "source": "rag",                  // cache | faq | rag | empty
  "strategy": "subquery",           // direct | hyde | subquery | step_back | null
  "model": "deepseek-chat",
  "chunks": [                       // 只存引用，不存全文（控 LIST 体积）
    { "chunk_id": "1024", "doc_name": "员工手册2026版.pdf", "page": 12, "score": 0.91 }
  ],
  "prompt_tokens": 1820,
  "completion_tokens": 340,
  "latency_ms": 856,
  "compress": { "method": "none", "dropped": 0 }   // 压缩方式与被丢弃片段数（装配侧产出）
}
```

- `turn_id`：`uuid.uuid4().hex`，一轮一个，两条消息共享。
- `chunks` 只存**引用**：`doc_name/page/score` 已足够支撑审计溯源与 RAGAS 的 `contexts` 回溯；存全文会让 LIST 元素膨胀（见 §14）。

### 5.3 MySQL：`rag_turn` 明细表（一轮两条，与 Redis 元素 1:1）

```sql
CREATE TABLE rag_turn (
  id                BIGINT NOT NULL COMMENT '主键' AUTO_INCREMENT,
  turn_id           VARCHAR(32) NOT NULL COMMENT '一轮问答ID（同一轮 user/assistant 两条共享）',
  user_id           VARCHAR(64) NOT NULL COMMENT '用户ID（网关下发，全局唯一）',
  session_id        VARCHAR(64) NOT NULL COMMENT '会话ID',
  tenant_id         BIGINT NOT NULL COMMENT '租户ID（仅统计用，不作为隔离条件）',
  role              VARCHAR(16) NOT NULL COMMENT '消息角色：user | assistant',
  content           MEDIUMTEXT NOT NULL COMMENT '消息正文',
  intent            VARCHAR(32) NULL COMMENT '意图：通用知识 | 专业咨询',
  source            VARCHAR(16) NULL COMMENT '产出来源：cache | faq | rag | empty（仅 assistant）',
  strategy          VARCHAR(32) NULL COMMENT '检索策略：direct | hyde | subquery | step_back（仅 assistant）',
  model             VARCHAR(64) NULL COMMENT '生成模型名（仅 assistant）',
  chunks_json       MEDIUMTEXT NULL COMMENT '召回片段引用 JSON 数组 [{chunk_id,doc_name,page,score}]（仅 assistant）',
  prompt_tokens     INTEGER NULL COMMENT '提示词 token 数（仅 assistant）',
  completion_tokens INTEGER NULL COMMENT '生成 token 数（仅 assistant）',
  latency_ms        INTEGER NULL COMMENT '端到端耗时毫秒（仅 assistant）',
  compress_method   VARCHAR(16) NULL COMMENT '上下文压缩方式：none | truncate | select | llm_summary（仅 assistant）',
  compress_dropped  INTEGER NULL COMMENT '压缩丢弃的片段数（仅 assistant）',
  eval_flag         TINYINT NOT NULL COMMENT '是否已纳入评测采样：0 否 1 是（RAGAS 用，见 §9）',
  created_at        DATETIME NOT NULL COMMENT '创建时间',
  PRIMARY KEY (id),
  CONSTRAINT uk_turn_role UNIQUE (turn_id, role)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='问答明细（一轮两条：user/assistant；与 Redis 会话原文 1:1）';
CREATE INDEX idx_user_session ON rag_turn (user_id, session_id);
CREATE INDEX idx_tenant_created ON rag_turn (tenant_id, created_at);
CREATE INDEX idx_created ON rag_turn (created_at);
```

- **唯一键 `uk_turn_role`**：重试/重放时靠它做幂等（`ON DUPLICATE KEY` 忽略），避免同一条消息写两遍。
- **为什么加 `tenant_id` 而 `rag_session` 不加**：`rag_session` 是会话实体，按 `user_id` 隔离即可；`rag_turn` 还要支撑「租户维度的命中来源分布 / FAQ 命中率 / RAG 占比」统计，租户 ID 在请求上下文里现成可取，作为**统计列**带上，不参与任何隔离过滤。
- **为什么 `chunks_json` 用 MEDIUMTEXT 而非 JSON 类型**：与既有表（`rag_api_call_log` 等）保持一致，序列化在 Python 侧做，避免不同 MySQL 版本 JSON 函数差异。
- **`eval_flag`**：RAGAS 不需要全量跑，采样标记留在这张业务表上代价最小（见 §9）。

### 5.4 ORM 模型（`store/orm_models/session.py` 新增）

```python

    user_id: Mapped[str] = mapped_column(String(64), nullable=False, comment='用户ID')

    tenant_id: Mapped[int] = mapped_column(BigInteger, nullable=False, default=0, comment='租户ID（仅统计）')

    __table_args__ = (
        UniqueConstraint('turn_id', 'role', name='uk_turn_role'),

        Index('idx_tenant_created', 'tenant_id', 'created_at'),
        Index('idx_created', 'created_at'),

```

同时更新 `scripts/gen_schema.py` 的 `SECTIONS`：把 `rag_turn` 放进「2) 用户级表」，并把该分区标题改为「用户级表（按 user_id 隔离；rag_turn 另带 tenant_id 仅统计用）」，然后重新生成 `scripts/schema.sql`。

### 5.5 记忆（memory）的存储归属

| 项 | 归属 | 说明 |
|---|---|---|
| 记忆实体存哪 | **本文档** | Redis `u:{user}:sess:{sid}:memory`，`{summary, facts, updated_at}` |
| `rag_session.memory_summary` 冗余 | **本文档** | 会话列表要展示"记住了什么"，compaction 后由 `core/session` 回写该列（截断到 512 字符） |
| 记忆 TTL | **本文档** | `config.REDIS_TTL_MEMORY`，过期即视为无记忆 |
| compaction 何时触发、提示词怎么写 | 架构决策文档 §2.4 | 每 4 轮，本设计不介入 |
| 记忆怎么注入 prompt、超限怎么裁 | 压缩文档 §4 | 本设计只保证 `get()` 能取到完整记忆 |

### 5.6 三层数据关系

```
MySQL rag_session (1) ──< rag_turn (N)        # 一轮两条，turn_id 关联同轮
       │
       └── 冗余：title / preview / memory_summary / turn_count（列表读这一行即可）

Redis  u:{user}:sess:{sid}        LIST  ← 消息原文（热路径，装配侧 get_history 从这里读）
Redis  u:{user}:sess:{sid}:memory STRING ← 记忆（装配侧 MemoryStore.get 从这里读）
```

## 6. 写入流程（细则）

### 6.1 时序

```
answer / answer_stream
  │
  ├─ 进入时生成 turn_id = uuid4().hex，随请求流转（不落库失败也要保证幂等键存在）
  │
  ├─ 出口处（拿到 answer / chunks / intent / source / strategy / model / tokens / latency）
  │    └─ _persist_session(...)
  │         1. 若 QA_PERSIST_ENABLED=false → 直接 return（保持 no-op 语义）
  │         2. 构造两条 turn dict：user 一条、assistant 一条
  │         3. QA_PERSIST_ASYNC=true → asyncio.create_task(写) 并持有引用防 GC
  │            false → await 同步写（便于单测与排障）
  │
  └─ 写入内容（同一协程内按序）：
      a. Redis RPUSH  u:{user}:sess:{sid}   ×2（user、assistant）
      b. Redis EXPIRE u:{user}:sess:{sid}   → 续期到 content_ttl
      c. Redis LTRIM  u:{user}:sess:{sid}   保留最近 QA_PERSIST_MAX_TURNS 条
      d. MySQL INSERT rag_turn ×2（uk_turn_role 幂等，冲突忽略）
      e. MySQL rag_session upsert：turn_count +1、preview=本轮 answer 截断、首轮写 title
```

### 6.2 分支覆盖（哪些出口要落库）

| 出口 | 是否落库 | `source` | 说明 |
|---|---|---|---|
| 答案缓存命中 | 是 | `cache` | 审计完整性优先：用户确实"问了并得到了答案" |
| FAQ 命中 | 是 | `faq` | 同上，`chunks` 为空 |
| RAG 生成 | 是 | `rag` | 带 `chunks` 引用与压缩信息 |
| 检索无命中 | 是 | `empty` | 记录"没答上来"，是知识库补漏的输入 |
| 空 query | 否 | — | 直接短路返回，不产生轮次 |

### 6.3 异步化与背压

- 用 `asyncio.create_task` 投递，并**持有 task 引用集合**（否则可能被 GC），完成后 discard。
- 并发上限 `QA_PERSIST_MAX_CONCURRENCY`（默认 32）：超出时丢弃并 `logger.warning`，宁可丢明细也不拖慢主链路。
- 不引入新的消息队列：当前量级下进程内异步足够；若后续需要跨实例可靠投递，再换 Celery/ARQ（与异步索引 Worker 统一选型）。

### 6.4 首轮标题与 preview

- `title`：首轮 `user` 消息前 N 字截断去标点（`core/session` 已实现），异步 LLM 润色可选；用户 `PATCH` 可改。
- `preview`：本轮 `answer` 截断到 512 字符回写 `rag_session.preview`。
- 两者都走 `SessionStore.registry_upsert`，不新增写路径。

## 7. 读取与查询场景

| 场景 | 读哪里 | 说明 |
|---|---|---|
| 会话列表 | MySQL `rag_session` | 已有实现，不变 |
| 会话详情/回看 | Redis LIST（优先）+ MySQL `rag_turn` 兜底 | Redis TTL 过期后仍能回看明细，这是建 `rag_turn` 的主要理由 |
| 问答明细导出（审计抽查） | MySQL `rag_turn` | 按 `(user_id, session_id)` 或时间范围查 |
| 运营统计 | MySQL `rag_turn` 聚合 | 按 `tenant_id` 统计 source 分布、FAQ 命中率、RAG 占比、p95 延迟 |
| RAGAS 评测取数 | MySQL `rag_turn` | 按 `eval_flag` 采样，见 §9 |
| 多轮上下文装配 | Redis LIST + `:memory` | **压缩文档负责，不读 `rag_turn`** |

---

## 8. 不做用户打分

- 不提供"用户对回答打分"的能力：没有 `record_rating` 入口，落库结构里也没有 `rating` 字段。
- 理由：评分属于质量评估范畴，全部交给 RAGAS 评测管道（见 §9）；业务存储只负责原样落库，不做质量计算与回写。

## 9. 为 RAGAS 预留的位置

**原则**：本设计只保证「RAGAS 需要的数据落得下来、取得出来」，不代做评测计算，评测结果也不回写业务表。

### 9.1 评测输入契约

RAGAS 的单条样本需要 `question / answer / contexts[] / (ground_truth)`。本设计已覆盖的位置：

| RAGAS 字段 | 来源 |
|---|---|
| `question` | `rag_turn` 中 `role='user'` 的 `content`（按 `turn_id` 配对） |
| `answer` | 同 `turn_id` 下 `role='assistant'` 的 `content` |
| `contexts[]` | `chunks_json` 的 `chunk_id` → 反查 `rag_chunk.content` 取回全文 |
| `ground_truth` | 评测集人工标注，存评测侧（见 9.2），**不进业务库** |

> 注意：Redis 与 `rag_turn` 只存 chunk **引用**，取全文需要按 `chunk_id` 回查 `rag_chunk`。这是有意的取舍——明细表不复制检索内容，避免同一份文本多处存储后版本不一致。

### 9.2 预留表（**暂不建**，RAGAS 落地时启用）

```sql
-- 评测集：人工/半自动标注的标准问答对
CREATE TABLE rag_eval_dataset (
  id            BIGINT NOT NULL COMMENT '主键' AUTO_INCREMENT,
  tenant_id     BIGINT NOT NULL COMMENT '租户ID',
  question      VARCHAR(1024) NOT NULL COMMENT '评测问题',
  ground_truth  MEDIUMTEXT NULL COMMENT '标准答案或关键要点',
  source_turn_id VARCHAR(32) NULL COMMENT '来源 turn_id（从真实问答里挑的样本，可空）',
  created_at    DATETIME NOT NULL COMMENT '创建时间',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='RAGAS 评测集（人工标注，评测侧数据）';

-- 评测结果：每次评测运行的分值与明细
CREATE TABLE rag_eval_run (
  id                BIGINT NOT NULL COMMENT '主键' AUTO_INCREMENT,
  run_id            VARCHAR(32) NOT NULL COMMENT '一次评测运行ID',
  turn_id           VARCHAR(32) NULL COMMENT '被评测的 turn_id',
  dataset_id        BIGINT NULL COMMENT '评测集样本ID（走评测集时非空）',
  faithfulness      DECIMAL(5,4) NULL COMMENT '忠实度：回答是否忠于上下文',
  answer_relevancy  DECIMAL(5,4) NULL COMMENT '相关性：回答是否切题',
  context_recall    DECIMAL(5,4) NULL COMMENT '上下文召回：证据是否捞全',
  raw_json          MEDIUMTEXT NULL COMMENT 'RAGAS 原始输出',
  created_at        DATETIME NOT NULL COMMENT '创建时间',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='RAGAS 评测结果（评测侧数据，不回写业务表）';
```

- 这两张表归「评测侧」，与业务表物理同库但逻辑分离，业务链路永不读写。
- 落地时机：RAGAS 接入时另立评测文档，届时再 `store/orm_models/` 加模型并重跑 `gen_schema.py`。

### 9.3 采集入口

- 问答链路里的评测信号采集点统一是 `core/qa_router/router.py::_audit_llm_result`（当前 no-op）。
- 落地方式：`_audit_llm_result` 按 `QA_EVAL_SAMPLE_RATE` 抽样，命中的 `turn_id` 回写 `rag_turn.eval_flag=1`，评测管道扫 `eval_flag=1` 的行取数。
- 业务库不做任何指标计算，`rag_eval_run` 的结果也不回写 `rag_turn`。

## 10. 配置（`common/config.py`）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `QA_PERSIST_ENABLED` | `true` | 总开关；false 时 `_persist_session` 直接返回（保持 no-op 行为，便于灰度） |
| `QA_PERSIST_ASYNC` | `true` | 是否异步落库；false 走同步 await（单测/排障用） |
| `QA_PERSIST_MAX_TURNS` | `400` | Redis LIST 单会话保留的**消息条数**（一轮 2 条，约 200 轮），超出 LTRIM |
| `QA_PERSIST_MAX_CONCURRENCY` | `32` | 异步落库并发上限，超出丢弃并告警 |
| `QA_PERSIST_CHUNK_FULLTEXT` | `false` | `chunks_json` 是否附带片段全文；默认只存引用 |
| `QA_EVAL_SAMPLE_RATE` | `0.05` | 评测采样率，`_audit_llm_result` 命中时置 `eval_flag=1` |

## 11. 可观测性

- 指标：落库耗时（p95）、失败率、丢弃数（超并发被丢）、单会话消息数分布、Redis LIST 大 key 告警。
- 日志：落库失败 `logger.warning`（含 `session_id` 与 `turn_id`，`content` 不落日志）。
- 对账（可选，定期）：随机抽样比对 Redis LIST 条数与 `rag_turn` 行数，差异超阈值告警。

---

## 12. 安全合规与保留期

- **PII 脱敏**：`content` 可能含用户隐私；敏感场景落库前做最小化或加密存储（KMS），日志只记 `session_id/turn_id`。
- **保留期**：Redis 原文 TTL=30d（热数据）；`rag_turn` 建议 180d 后归档/清理，保留策略由运维脚本执行，不在应用内做定时删除。
- **删除联动**：`DELETE /v1/sessions/{id}` 需同时清 Redis 原文、`:memory`、索引 SET，并删 `rag_session` 行与 `rag_turn` 行（按 `session_id`）。
- **隔离**：所有查询带 `user_id`；`tenant_id` 只出现在统计 SQL 里。

---

## 13. 容错降级

- 落库异常被捕获，`logger.warning` 后返回，**绝不**抛到主链路。
- Redis 写失败 → 仍写 MySQL（明细不丢）；MySQL 写失败 → 仍写 Redis（当轮对话不丢）；双写都失败只记日志，不重试阻塞。
- `uk_turn_role` 冲突视为成功（幂等），不告警。

---

## 14. 性能与成本

- 主路径新增开销：2 次 Redis RPUSH + 1 次 EXPIRE + 1 次 LTRIM + 2 次 MySQL INSERT + 1 次 upsert，全部异步，不影响首 token 与最终响应延迟。
- `chunks_json` 只存引用：一轮约 200–500 字节；若开启全文会放大 10 倍以上，默认关。
- 存储量粗估：按单租户日均 1 万轮、`rag_turn` 单行约 1KB 计，月增约 600MB，落在 180d 保留策略内需规划归档。

## 16. 风险与开放问题

- **Redis key 与架构决策文档不一致**：代码是 `u:{user}:sess:{sid}`，文档写的是带租户段。本轮按代码走，但要决定是改文档还是改 key（改 key 需存量迁移）。
- **双写一致性**：Redis 与 MySQL 最终一致；异步写失败会丢 MySQL 明细，靠对账发现。
- **chunks 只存引用**：抽查时要回查 `rag_chunk`，若该 chunk 已被删除（文档下线），溯源信息会失效；可考虑在 `chunks_json` 里冗余 `doc_name/page` 文本（已做）但正文不保证。
- **`rag_turn` 归属分区**：表带 `tenant_id` 但按 `user_id` 隔离，放在"用户级表"分区需在标题里说明，避免后人误以为可按租户隔离查询。
- **评测采样**：`eval_flag` 写回会产生一次额外 UPDATE；量大时可改为评测管道侧随机抽样，不在业务表落标记。
