# 配置中心对接设计

> 版本：v1.6 ｜ 日期：2026-10-18 ｜ 依据《智能体平台-RAG架构设计 v5.1》（含 Nacos 配置中心决策变更）
> 说明：本文聚焦"对接 Nacos 配置中心"的通用能力（变量分离、存储复用、审批流、控制台接口、一致性）。提示词等具体业务配置将在此对接基础上另行设计文档，本文不展开业务配置语义。
> v1.1 修正：控制台**仅查询类接口直连 Nacos**；变更类（申请执行、回滚）必须走审批流，由后端代理调 Nacos 写，控制台不直接执行 Nacos 写操作。

---

## 0. 背景与架构边界

- **接入 Nacos 配置中心**：命名空间 `rag-ultra`（配置中心专用）。
- **服务发现 与 配置中心 变量配置独立分开**：服务发现沿用 `app/managers/nacos_discover_manager.py`（namespace=`public`，变量 `NACOS_*`）；配置中心新增独立客户端（namespace 取 `config.NACOS_CONFIG_NAMESPACE`，显示名为 `rag-ultra`，变量 `NACOS_CONFIG_*`）。
- **配置中心为系统级通用配置，不按租户隔离**：由运维人员（admin / operator 角色）维护，非租户自助；value 按 `domain`（prompt/faq/kb...）分桶承载多类配置。
- **管控/审批自建 MySQL，存储与历史复用 Nacos**：Nacos 仅作配置存储与历史落库；审批流（申请/复核）是业务管控，Nacos 无此语义，需自建。

### 0.1 配置组织（group 约定）

配置按 **group** 维度分桶，便于分类管理与权限收敛。代码侧只做**通用、group 参数化**的查询抽象
（`core/config_center/query.py` 的 `list_by_group(group, ...)` / `get_detail(group, data_id)`），
**不按 group 写专门分支**——group 只是入参。

| group | 用途 |
|---|---|
| `SYSTEM` | 系统级配置（全局开关、运行参数等） |
| `PROMPT` | 提示词专用（如 `prompt.qa.system.json`） |

读写路径：
- 只读列表 / 详情：走 `query.list_by_group` / `query.get_detail`（底层 Nacos `/nacos/v3/admin/cs/config`）。
- 业务侧热加载：经 `ConfigCenterLoader.get_json(data_id, group)` 按 data_id 后缀兼容 json/yaml；按 group 取列表则走 `query.list_by_group`。
- group 由代码枚举 `core/config_center/groups.py:ConfigGroup` 统一定义，新增分组只需追加枚举成员（如 `PROMPT = "PROMPT"`），业务侧引用枚举而非硬编码字符串。

## 1. Nacos 配置中心在 MySQL 用到的表（整理 + 复用策略）

Nacos 配置中心底层依赖自己的 MySQL schema（节选自 Nacos 官方 `nacos-mysql.sql`，2.x）。与"配置中心对接"相关的表：

| Nacos 表 | 作用 | 本项目复用方式 |
|---|---|---|
| `config_info` | **当前生效配置**（主表） | 复用：调 Nacos API 读写，不本地存；当前态以它为准 |
| `his_config_info` | **配置历史/审计**（每次变更自动插记录） | **复用（替代自建历史表）**：历史/审计/回滚均读此表 |
| `config_info_beta` | 灰度配置 | 可选复用：未来灰度发布直接用 Nacos beta |
| `config_info_tag` / `config_tags_relation` | 配置标签 | 可选：按业务打标 |
| `config_info_aggr` | 聚合配置（大配置分片） | Nacos 内部用，业务不感知 |
| `tenant_info` | 命名空间（tenant/namespace）信息 | 复用：`rag-ultra` 由 Nacos 管理，不需自建 |
| `tenant_capacity` / `group_capacity` | 容量配额 | Nacos 内部用 |

**关键：Nacos 内部以 `tenant_id` 字段存储命名空间**（rag-ultra 即 `tenant_id='rag-ultra'`）。

### 1.1 `his_config_info` 字段 ↔ 审计需求（完全覆盖）

Nacos 历史表天然含审计所需全部字段，无需自建历史表：

| 审计需求字段 | `his_config_info` 对应列 | 说明 |
|---|---|---|
| 命名空间 | `tenant_id` | = rag-ultra |
| group | `group_id` | Nacos group |
| dataId | `data_id` | 配置项 key |
| 配置内容 | `content` | 审计核心 |
| 操作人 | `src_user` | 实际执行人 |
| 创建时间 | `gmt_create` | 历史记录创建 |
| 更改时间 | `gmt_modified` | 记录更新 |
| 增删改类型 | `op_type` | 1=新增 2=修改 3=删除 |
| 内容指纹 | `md5` | 比对/去重 |
| 历史ID | `nid` | 回滚定位 |
| 关联当前配置 | `id` | 对应 `config_info.id` |

→ **结论：历史/审计/回滚均复用 `his_config_info`**，前端查询历史、历史详情直接走 Nacos 历史 API；回滚的**执行**由后端在审批通过后代理调用 Nacos（控制台不直接回滚）。

## 2. 数据模型（MySQL，仅自建"审批流"两层）

只自建 Nacos **没有**的审批语义表；当前态/历史由 Nacos 表承担。不再自建历史表（`config_history`），避免双写不一致。实际建表以 `scripts/schema.sql` 为准（表名统一带 `rag_` 前缀、每列含 COMMENT）。

### 2.1 配置变更申请（自建，表名 `rag_config_change_request`）

```sql
CREATE TABLE rag_config_change_request (
  id          BIGINT PRIMARY KEY,
  namespace   VARCHAR(128) NOT NULL,            -- Nacos 命名空间（如 rag-ultra，对应 Nacos tenant_id）
  group_id    VARCHAR(128) NOT NULL DEFAULT 'DEFAULT_GROUP',
  data_id     VARCHAR(256) NOT NULL,            -- Nacos dataId（配置项 key）
  domain      VARCHAR(32)  NOT NULL,            -- 配置域: prompt / faq / kb ...（通用分类）
  op_type     TINYINT      NOT NULL,            -- 1=新增 2=修改 3=删除 4=回滚
  title       VARCHAR(256),
  content_new      MEDIUMTEXT,                  -- 拟下发内容全文（审批前未进 Nacos、无 id 可关联，必须存本地）；新增/修改/回滚时填写，删除时为空
  old_config_id    BIGINT,                      -- 变更前在 Nacos 的引用：提交申请时抓取的 config_info.id（新增时为空）；审批展示旧内容据此实时拉 Nacos 当前态
  old_config_md5   VARCHAR(64),                  -- 申请时 Nacos 当前 md5（CAS 乐观锁基准，非冗余内容）
  old_history_nid  BIGINT,                      -- 执行成功后回填：Nacos 把变更前内容归档为历史(his_config_info.nid)，供后续追溯旧版本
  content_format   VARCHAR(16) NOT NULL DEFAULT 'json', -- 内容格式: json/text/yaml，供前端渲染与 diff
  src_history_nid  BIGINT,                      -- 回滚类申请：来源历史 nid（his_config_info.nid）；content_new 取自该历史快照
  status      TINYINT      NOT NULL DEFAULT 0,  -- 0=待复核 1=已通过 2=已驳回 3=已执行(Nacos已写)
  applicant   VARCHAR(64),                      -- 申请人（操作人）
  reviewer     VARCHAR(64),                      -- 复核人
  reason      VARCHAR(512),
  nacos_history_nid BIGINT,                     -- 审批通过执行后回填的 his_config_info.nid（关联 Nacos 历史）
  created_at  DATETIME,
  updated_at  DATETIME,
  KEY idx_status (status),
  KEY idx_domain (domain),
  KEY idx_data (namespace, group_id, data_id)
);
```

### 2.2 配置复核记录（自建，表名 `rag_config_review`）

```sql
CREATE TABLE rag_config_review (
  id          BIGINT PRIMARY KEY,
  request_id  BIGINT       NOT NULL,
  reviewer    VARCHAR(64),             -- 复核人（操作人）
  action      TINYINT      NOT NULL,   -- 1=通过 2=驳回
  comment     VARCHAR(512),
  created_at  DATETIME,
  updated_at  DATETIME,
  KEY idx_request (request_id)
);
```

> 历史/审计 = Nacos `his_config_info`（权威源）。审批通过执行 Nacos API 时，Nacos 自动写 `config_info` + `his_config_info`，**单一数据源，无双写不一致**。申请单通过 `nacos_history_nid` 关联 Nacos 历史记录；回滚类申请用 `src_history_nid` 指向被回滚的历史。

### 2.3 审批展示与新旧对比（数据库层面）

审批人在复核时按操作类型查看变更内容：修改/回滚需**前后对比**，新增/删除仅单向展示（无对比另一方）。差异（diff）计算交给前端，后端只负责把"展示所需的数据"从数据库返回。

- **内容存储策略（为何不全用 id 关联）**：
  - `content_new`（拟下发内容）：**审批前尚未写入 Nacos**，Nacos 中无此内容、无 id 可关联，必须以全文存于申请单；审批通过后由 `ConfigChangeService` 写入 Nacos 才产生 id/历史。
  - 变更前内容（`old`）：**可用 id 关联、不冗余全文**——提交申请时记录 Nacos 当前 `config_info.id`（`old_config_id`）；审批展示"旧内容"据此实时从 Nacos 拉取当前态（配置中心受审批流管控，审批期间不应被绕过修改，基于最新当前态审批更合理）；执行成功后 Nacos 把变更前内容归档为 `his_config_info`，回填 `old_history_nid` 供后续追溯。
- `content_format`（`json` / `text` / `yaml`）告知前端使用何种渲染器与 diff 算法（JSON 结构化对比 vs 纯文本行级 diff）。
- **仅"修改/回滚"存在新旧双方，需做前后对比（diff）；"新增/删除"为单向变更，只有一侧内容，前端不展示 diff 面板**。
- 各 `op_type` 字段填充约定：

| op_type | 旧内容来源 | content_new | 是否对比 | 审批展示语义 |
|---|---|---|---|---|
| 1=新增 | 无（`old_config_id` 空） | 新内容全文 | 否（单向） | 仅展示"将新增的内容" |
| 2=修改 | Nacos 当前 `config_info`（`old_config_id` 引用） | 新内容全文 | 是 | 前后对比（旧=实时拉 Nacos，新=本单） |
| 3=删除 | Nacos 当前 `config_info`（`old_config_id` 引用） | 空 | 否（单向） | 仅展示"将被删除的内容" |
| 4=回滚 | 当前内容（`old_config_id`） | 历史快照内容（`src_history_nid`，全文存本单） | 是 | 前后对比（diff，回滚到历史版本） |

## 3. 总体流程（审批自建 + 历史复用 Nacos）

```
【变更流程】
前端控制台(M7, 运维角色)
   │ 发起"配置变更申请"(增/删/改: namespace/group/dataId/domain/content)
   ▼
MySQL: rag_config_change_request (status=待复核, old_config_id 记录 Nacos 当前 config_info.id，旧内容实时从 Nacos 拉取)
   │
复核人 ──复核(通过/驳回)──> MySQL: rag_config_review
   │ 通过 → status=已通过(APPROVED)
   ▼
执行人 ──POST /admin/config/requests/{id}/execute──> ConfigChangeService（代理调 Nacos，带 CAS）
   │ 成功：Nacos 自动写 config_info(当前) + his_config_info(历史)
   ▼
回填 rag_config_change_request.nacos_history_nid + status=已执行（回填为空时 sync_history_nids 补偿）
   │
   ▼ Nacos watcher 推送各实例 ──> 业务读取(core) 热加载新配置

【回滚流程】（同样是变更，必经审批）
前端 ──POST /admin/config/rollback（指定 src_history_nid）──> 生成回滚申请(op_type=4)
   │ 复核通过 ──> ConfigChangeService 代理调 Nacos 回滚(按 nid) ──> Nacos 写 config_info+his_config_info
```

## 4. Nacos 配置中心对接（变量分离、API 封装）

- 复用 `nacos-sdk-python`；新增 `core/config_center/nacos_config.py`：`ConfigCenterClient`（命名空间取 `config.NACOS_CONFIG_NAMESPACE`），与 `NacosDiscoverManager` 服务发现独立。
- `common/config.py` 新增 `NACOS_CONFIG_*`（不改动 `NACOS_*`）：

```python
# Nacos 配置中心（独立命名空间，与"服务发现"的 NACOS_* 分离）
NACOS_CONFIG_ENABLED:      bool = True
NACOS_CONFIG_SERVER_ADDR:  str = 'http://localhost:8848'
NACOS_CONFIG_NAMESPACE:    str = '<命名空间 ID>'   # 唯一来源：其余模块一律读 config，不各写一份
NACOS_CONFIG_GROUP:        str = 'DEFAULT_GROUP'
NACOS_CONFIG_USER:         str = ''
NACOS_CONFIG_PASSWORD:     str = ''
```

> **命名空间填 ID，不是显示名**：Nacos 自定义命名空间的 ID 默认是 UUID（本项目显示名 `rag-ultra`
> 对应 ID `394fd817-…`），控制台列表里 `namespace` 才是 ID、`namespaceShowName` 是显示名。
> 填显示名会静默指向一个不存在的命名空间，读不到任何配置且不报错——排查时优先核对这一项。
> 部署环境用 `.env` 的 `NACOS_CONFIG_NAMESPACE` 覆盖，`common/config.py` 只放兜底默认值。

- API 封装（**写类仅由后端 ConfigChangeService 在审批通过后调用，控制台不直接调用**）：

| 类别 | 操作 | 方法 / Open API | 说明 |
|---|---|---|---|
| 读 | 获取命名空间列表 | `GET /nacos/v3/admin/core/namespace/list` | 控制台直连查询；也用于把显示名（rag-ultra）解析成 UUID |
| 读 | 配置列表 | `GET /nacos/v3/admin/cs/config/list?dataId=&group=&namespaceId=&pageNo=&pageSize=` | 指定命名空间查配置（直连） |
| 读 | 配置详情 | `GET /nacos/v3/admin/cs/config?dataId=&group=&namespaceId=` | 某配置当前内容（直连） |
| 读 | 历史列表 | `GET /nacos/v3/admin/cs/history/list?dataId=&group=&namespaceId=&pageNo=&pageSize=` | 读 `his_config_info`（直连） |
| 读 | 历史详情 | `GET /nacos/v3/admin/cs/history?dataId=&group=&namespaceId=&nid=` | 单条历史（直连），参数是 `nid` 不是 `id` |
| 写 | 发布/更新 | `POST /nacos/v3/admin/cs/config?dataId=&group=&namespaceId=&content=` | 后端代理（审批通过后） |
| 写 | 删除 | `DELETE /nacos/v3/admin/cs/config?dataId=&group=&namespaceId=` | 后端代理（审批通过后） |
| 写 | 回滚 | 先按 `nid` 取历史详情拿 `content`，再走发布接口 | **后端代理**（审批通过后，非控制台直连） |

- 读类走 Nacos Open API（控制台经后端代理直连查）；写类封装在 `ConfigChangeService`，仅在复核通过时触发。

### 4.1 服务端版本 3.x 的适配要点

服务端为 **Nacos 3.2.x**，与 2.x 相比有几处 breaking change，代码已按此适配：

- **命名空间 id 必须是 UUID**：配置里的 `rag-ultra` 是显示名（`namespaceShowName`），调 SDK 前需经
  `common/nacos_compat.py:resolve_namespace_id` 换成 UUID；公共命名空间 `public` 映射为空串。
- **SDK 用 2.0+（`v2.nacos`，全异步、走 gRPC）**：`nacos-sdk-python<2` 走 v1 HTTP 注册接口，
  在 3.x 上会返回 `501 Not Implemented`。依赖固定为 `nacos-sdk-python>=2`。
  - 服务发现：`NacosNamingService` + `RegisterInstanceParam`；心跳由 SDK 长连接维持，不再自建心跳循环。
  - 配置热加载：`NacosConfigService`，`get_config` / `add_listener` 均为 coroutine，监听回调是
    async 且签名为 `(tenant, group, data_id, content)`。
- **回滚端点已移除**：3.x 没有 `/v3/admin/cs/history/rollback`，回滚改为「取历史内容 + 重新发布」。
- 注册失败的兜底：`NACOS_DISCOVER_STRICT=False`（默认）时只告警不阻断启动。

## 5. 控制台 API（M7，运维角色）

**接口边界**：查询类（只读）直连 Nacos；变更类（写）必须走审批流，由后端代理调 Nacos，控制台不直接执行 Nacos 写操作。

| Method | Path | 类别 | 说明 |
|---|---|---|---|
| GET | `/admin/config/namespaces` | 查询·直连Nacos | 获取命名空间列表 |
| GET | `/admin/config/list?namespace=&group=&dataId=` | 查询·直连Nacos | 指定命名空间查配置列表 |
| GET | `/admin/config/detail?namespace=&group=&dataId=` | 查询·直连Nacos | 某配置详细（当前内容） |
| GET | `/admin/config/history?namespace=&group=&dataId=&page` | 查询·直连Nacos | 查看历史（his_config_info） |
| GET | `/admin/config/history/{nid}` | 查询·直连Nacos | 历史详情 |
| POST | `/admin/config/requests` | 变更·审批流 | 发起配置变更申请（增/删/改） |
| GET | `/admin/config/requests` | 查询·MySQL | 申请列表（status/domain/operator） |
| GET | `/admin/config/requests/{id}` | 查询·MySQL | 申请详情（返回 content_old/content_new/content_format，供前端展示与 diff） |
| POST | `/admin/config/requests/{id}/review` | 变更·审批流 | 复核：通过(置待执行)/驳回 |
| POST | `/admin/config/requests/{id}/execute` | 变更·审批流 | 执行已通过的申请（真正写 Nacos，带 CAS） |
| POST | `/admin/config/requests/{id}/sync-history` | 变更·审批流 | 程序对齐：重拉 Nacos 历史回填 nid（自愈/补偿，无需人工） |
| POST | `/admin/config/rollback` | 变更·审批流 | 发起回滚申请（指定 src_history_nid），经复核后由后端代理调 Nacos 回滚 |

- 查询页：命名空间列表、配置列表/详情、历史与 diff 对比（直连 Nacos，只读无副作用）。
- 变更页：申请表单、待办复核、回滚入口（均落 MySQL 审批流，写操作不直连 Nacos）。

## 6. 一致性保障（为何复用 Nacos 历史 + 变更受控）

- **单一数据源**：当前态=`config_info`，历史=`his_config_info`，均由 Nacos 在 publish/remove/rollback 时原子写入；本地不冗余存配置内容/历史。
- **查询直连、变更受控**：只读查询（命名空间/列表/详情/历史）直连 Nacos，无副作用；任何写操作（增删改/回滚）必须发起申请→复核→后端代理执行，保证受控、可审计、与申请单一致。
- **审批流 ≠ 历史**：`rag_config_change_request`/`rag_config_review` 是"审批过程"记录（Nacos 无此语义），审批通过后**才**触发 Nacos 写，Nacos 产生权威历史；两表职责不重叠，无双写。
- **关联而非复制**：申请单记录 `nacos_history_nid` 指向 Nacos 历史，内容以 Nacos 为准，避免本地副本漂移。
- **回滚也受控**：回滚不是直连 Nacos 的写，而是发起回滚申请（带 `src_history_nid`），复核通过后由 `ConfigChangeService` 代理调 Nacos 回滚，Nacos 再生成一条历史，闭环一致。

### 6.1 并发控制（代码实现）

配置中心的操作均属**管理员权限、频率低、基本无高并发**，无需引入分布式锁 / 限流等重方案。并发控制采用**乐观锁或悲观锁**其一即可（代码层实现）：

- **乐观锁（推荐，基于 Nacos CAS）**：执行 `publish_config` / `remove_config` 时携带申请时抓取的当前内容 `md5` 作为 `casMd5`（Nacos 2.x 支持）。若执行时 Nacos 当前 `md5` 不一致，说明期间该配置已被改动，**拒绝执行**并提示"配置已被他人修改，请刷新后重新申请"，避免基于过期基准的覆盖写（lost update）。回滚执行同理：复核前置统一做 md5 比对（见 review 执行前校验），不一致即拒绝。
- **悲观锁（备选）**：对 `(namespace, group_id, data_id)` 相关记录加 DB 行锁（`SELECT ... FOR UPDATE`），保证同一配置项的变更串行提交。
- 两者二选一即可满足低频管理场景；申请单状态迁移（待复核→已执行）仍用普通事务 + `WHERE status=待复核` 保证不重复执行。

### 6.2 与 Nacos 库的一致性（引用 id 的保证）

`old_config_id` / `old_history_nid` / `nacos_history_nid` / `src_history_nid` 都是指向 Nacos 自己库（`config_info` / `his_config_info`）的"引用"：不是外键、也无法与 Nacos 做跨库事务一致——Nacos 才是权威源。一致性靠三层保证（已落地 `core/config_center/service.py`）：

- **真正兜底的是 md5-CAS，不是 `old_config_id` 本身**：`old_config_id` 只在申请时从 Nacos 抓一次；执行时不拿它当依据，而是重新拉 Nacos 当前配置比对 `old_config_md5`，不一致则拒绝执行（提示"配置已被他人修改"）；实际写 Nacos 还带 `casMd5`，Nacos 自身也会拒绝基于过期基准的覆盖写。即使 `old_config_id` 指向的记录已被改动，也只会"拒绝"，不会脏写。
- **历史 nid 在执行成功后从 Nacos 响应里抓**：写成功后立即 `list_history` 回填（`new_nid = max(nid)` 为新版本，`old_nid` 为 md5 命中 `old_config_md5` 的那一版），那一刻必然与 Nacos 库一致。
- **补偿（`sync_history_nids`）**：若 Nacos 写成功、但本地回填 nid 时网络抖动导致为空，可重新 `list_history` 把 nid 补回；Nacos 仍是权威，补偿不影响终态。

风险与边界：Nacos 有历史保留期，`his_config_info` 被清理后，存的 `old_history_nid` / `nacos_history_nid` 可能悬空——它们只用于展示/审计，且申请详情的旧内容始终实时从 Nacos 拉当前态，不依赖这些 nid。执行后若本地回填为空（Nacos 历史瞬时不可见），`service.execute_request` 会自动再调 `sync_history_nids` 补偿，保证 nid 最终一致。
