# 访问模型与会话架构决策

> 版本：v1.2 ｜ 日期：2026-10-19 ｜ 相较 v1.1：确认持久化路线（Redis 存原文 + PostgreSQL rag_session 注册表，表需新增）；确认 title 生成策略（首句截断+异步 LLM 润色）、compaction 参数（N=4、TTL=30d）、新增 DELETE；设计已对齐 rag-pro 与 Octop

本文汇总 RAG-Ultra 在"访问模型 / 会话隔离 / 检索策略 / 接口分包"上的关键决策，避免后续改动偏离已确认的设计。实现细节以代码为准。

## 1. 访问模型与隔离边界

```
租户 (tenant)
├── 多用户 (user)
│   └── 多会话 (session)         # 会话由 RAG_Ultra 服务端生成
└── 多文件 (file)                # 文件在运营后台维护
```

- 入口：后台 admin 端 → JAVA 侧网关 → **OAUTH 权限校验** → RAG-Ultra 问答接口。
- 网关下发请求头：`X-Tenant-Id` / `X-User-Id`（由 `app/api/deps.py` 的 `resolve_tenant` 解析并写入 contextvars）。
- 文件仅按租户隔离（MinIO key 前缀 `t{tenant_id}/`）；会话按 `(用户, 会话)` 两级隔离（user_id 由网关 OAuth 全局唯一下发，跨租户不重复，无需叠加租户）。

## 2. 会话：服务端生成 + 三级隔离 + 列表/记忆

> 设计参考（项目规则 `.codebuddy/rules/项目参考.mdc` 授权）：核心逻辑参考 `rag-pro`；会话/记忆/启动服务参考 `Octop`。**不引用** `RAGDemo` / `agent-platform` / `AgentCore` 等其他项目。对齐细节见 §2.6，落地方案见 §2.7。

### 2.1 会话实体模型
- 会话由 **RAG-Ultra 服务端生成** `session_id`，仅绑定 `user_id`（由网关 OAuth 全局唯一下发，跨租户不重复）；**同一用户可拥有多个会话**。
- 每个会话是一个独立实体，包含：
  - `session_id`：服务端 uuid（非客户端传入，参考 rag-pro 用 `uuid.uuid4().hex` 生成）
  - `title`：**会话标题**。首轮提问后自动生成：默认**首句截断**（前 N 字去标点，零成本）即时成标题；后台**异步 LLM 润色**（可选，不阻塞首轮）；用户可 `PATCH` 改
  - `created_at` / `updated_at`
  - `content`：多轮对话原文 `[{role, content, ts}]`（热路径，Redis 列表，复用 rag-pro 的 `prefix:session:{sid}` 模式）
  - `memory`：会话记忆（见 2.4），会话级长期上下文，独立于原始 content
- `user_id` **取自网关头 `X-User-Id`**，不从请求体传（防伪造）；未接网关时兜底为 `DEFAULT_USER_ID`（默认 1001），
  关闭 `IDENTITY_DEFAULT_ENABLED` 后缺 `X-User-Id` 的会话接口返回 401。

### 2.2 存储（content 走 Redis，注册表落 PostgreSQL）
会话数据按职责拆分存储（对照 rag-pro 存原文 + Octop 把会话当 DB 实体）：
```
t:{tenant}:u:{user}:sess:{sid}        → 对话原文 LIST（RPUSH，TTL=30d，复用 rag-pro 的 Redis 列表模式）
t:{tenant}:u:{user}:sess:{sid}:memory  → {summary, facts:[...], updated_at}（会话记忆，独立子系统）
t:{tenant}:u:{user}:sessions          → 会话索引 SET（热路径辅助；列表以 PostgreSQL 为准）
```
- **PostgreSQL `rag_session` 表**（见 §2.7 DDL）：会话注册表/索引，存 `title / preview / memory_summary / turn_count / 时间`，按 `user_id` 过滤做列表。**保证列表可长期回看，不受 Redis TTL 影响**（对齐 Octop 的会话 DB 实体）。
- 对话原文仍留 Redis（热路径低延迟 + TTL 自动清冷数据），不照搬 Octop 把全文落 DB。
> 因此 **建表脚本（schema_postgresql.sql）需新增 `rag_session` 表**（修正 v1.1"SQL 无需改动"的结论——需求升级为"可回看列表"后，注册表必须持久化）。

### 2.3 会话列表（GET /v1/sessions）
返回当前用户全部会话的**轻量视图**，每项包含：
```json
{ "session_id", "title", "preview", "memory_summary",
  "turn_count", "created_at", "updated_at" }
```
- 列表数据来自 **PostgreSQL `rag_session`**，跨用户不可见（按 `user_id` 隔离）。
- `preview`：最近一条或摘要，避免列表返回完整 content 造成大 payload；完整内容走 `GET /v1/sessions/{id}`。
- `memory_summary`：记忆摘要，便于用户快速回顾每个会话"聊了什么/记住了什么"。

### 2.4 会话记忆（memory）的生成与注入
- **定义**：会话级长期上下文（**独立子系统**，类比 Octop 的 `octop_memory.core.Memory`，与对话原文分离存储），弥补"仅取最近 K 轮"的窗口限制。包含：
  - `summary`：滚动摘要，通过**记忆压缩(compaction)** 重算，避免无界增长
  - `facts`：从对话中抽取的用户偏好 / 关键实体 / 待办等结构化事实
- **生成（compaction，已确认 N=4、content TTL=30d）**：每 4 轮（或距上次压缩 > M 分钟）触发一次 LLM，对 `summary + facts` 做增量压缩更新并写回 `:memory`；**异步执行，不阻塞问答**，失败降级为跳过本次压缩；不在每轮调用以控成本（与 Octop 记忆维护的 compacting / deduplicating 阶段思路一致）。
- **注入**：`core/rag_generator/generator.py` 组装上下文时，除最近 K 轮 history 外，额外拼入该会话的 `memory.summary` 与 `facts`，使回答具备跨窗口的长期一致性。
- **隔离**：memory 同样按 (tenant,user,session) 隔离，不跨会话/用户泄漏。

### 2.5 API 变更汇总（用户侧 app/api/user/routes_session.py）
| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/v1/sessions` | 可选 body `{title?}`；返回 `{session_id, title}`（同时写 PostgreSQL 注册表） |
| GET  | `/v1/sessions` | 列表（读 PostgreSQL）：title + preview + memory_summary + turn_count … |
| POST | `/v1/sessions/{id}/turns` | 追加一轮；首轮自动生成 title；累计轮数 + 异步触发 compaction |
| GET  | `/v1/sessions/{id}` | 返回 `{title, content, memory, created_at, updated_at}` |
| PATCH| `/v1/sessions/{id}` | 用户编辑 title |
| DELETE| `/v1/sessions/{id}` | 删除会话：清 Redis 原文 + memory + 删 PostgreSQL 注册表行 |

### 2.6 参考依据与设计对齐
本会话/记忆模型对齐以下两个**授权参考项目**的实现，而非凭空设计：

- **`rag-pro`（会话 / 核心逻辑）**：会话历史是 Redis LIST，键 `prefix:session:{session_id}`，元素 `{role, content}`；`get_chat_history(sid, max_turns)` 取最近 `2*max_turns` 条，`add_chat_history` 用 `rpush + expire`（TTL 默认 1 天），`session_id` 由 `uuid.uuid4().hex` 服务端生成。
  → 印证本设计"会话内容走 Redis 列表 + TTL"的选型；本设计在其基础上加 `用户` 隔离维度（user_id 全局唯一，无需叠加租户；rag-pro 为更简单的单级 key）。
- **`Octop`（会话 / 记忆 / 启动）**：
  - 会话是 **DB 实体**（`sessions` 表：`session_key / user_id / channel_metadata(JSON) / updated_at / unread_count`），支持 `list_by_agent` / `list_by_thread` / upsert → 对应本设计"会话注册表(`rag_session`) + 列表接口 + 单用户多会话"。本设计现采用 **PostgreSQL `rag_session` 注册表**对齐 Octop 落库做法（见 §2.7）。
  - 记忆是**独立子系统**（`octop_memory.core.Memory`，按 `agent_{id}` 命名空间，sqlite 后端，带 `compacting` / `deduplicating` 维护阶段）→ 对应本设计"记忆独立于对话原文、按 `(用户,会话)` 命名空间、节流压缩(compaction)"。

> 设计原则：复用授权参考项目的成熟模式（Redis 列表存对话、会话注册表落 DB、记忆独立且压缩），不引入未经验证的方案；其他项目不在参考范围内。

### 2.7 落地方案（已确认，待实现）
三个已确认决策：
1. **持久化路线**：Redis 存对话原文 + PostgreSQL `rag_session` 注册表（可长期回看列表）；不把全文落 DB。
2. **title 生成**：首句截断即时成标题 + 可选异步 LLM 润色；用户可改。
3. **compaction / TTL**：每 4 轮触发记忆压缩；content TTL=30 天。

PostgreSQL DDL（`scripts/schema_postgresql.sql` 新增）：
```sql
CREATE TABLE rag_session (
  id BIGSERIAL PRIMARY KEY,
  user_id   VARCHAR(64) NOT NULL,
  session_id VARCHAR(64) NOT NULL,
  title VARCHAR(255) NOT NULL DEFAULT '',
  preview VARCHAR(512) NOT NULL DEFAULT '',
  memory_summary VARCHAR(512) NOT NULL DEFAULT '',
  turn_count INT NOT NULL DEFAULT 0,
  created_at TIMESTAMP, updated_at TIMESTAMP,
  UNIQUE (user_id, session_id)
);
```

实现改动点（**已落地**）：
- 会话逻辑抽离至 **`core/session/`**：`session_store.py`（Redis 原文/元数据 + PostgreSQL `rag_session` 注册表）、`session_service.py`（编排、首轮标题生成、记忆压缩触发）、`models.py`（`SessionView`）。
- 记忆逻辑抽离至 **`core/session_memory/`**：`memory_store.py`（Redis 存 `{summary, facts}`）、`memory_service.py`（LLM compaction + 注入文本）、`models.py`（`SessionMemory`）。
- `store/orm_models/session.py`：新增 `RagSession` ORM；`scripts/schema_postgresql.sql` 新增 `rag_session` 表 DDL。
- `app/api/user/routes_session.py`：列表读 PostgreSQL 富字段；`POST /sessions` 写注册表；`turns` 累计轮数 + 异步触发 compaction；新增 `PATCH`（改标题）/ `DELETE`。
- `core/rag_generator/generator.py`：拼上下文时前置注入 `memory.summary` + `memory.facts`。
- 旧 `store/conversation_store.py` 已移除（功能迁入 `core/session`）。
- 单测：`tests/core/session/`、`tests/core/session_memory/` 配套 pytest + mock（遵循项目单测约定）。

## 3. 检索增强：四选一策略（非顺序串联）

- 策略枚举（`core/rag_retriever/strategy_selector.py`）：`直接检索 / 假设性文档嵌入检索(HyDE) / 子查询检索 / 回溯问题检索`。
- 由 LLM **四选一**，不是图中"改写→HyDE→多查询"的顺序串联。
- **理由（用户已确认保留）**：① 成本与延迟——顺序执行至少多 1–2 次 LLM 调用；② 策略互斥（回溯与子查询方向相反，不宜同跑）；③ 图是能力清单而非强制管道。
- 若需协同，只允许改 `core/rag_retriever/query_augmenter.py` 的编排，不动 `StrategySelector` 与 `router` 调用点。

## 4. API 分包隔离

- `app/api/user/`：终端用户接口（`/v1/qa`、`/v1/sessions/...`）。
- `app/api/dashboard/`：运营后台接口（文档 / FAQ / 文件 / 管理台 / 配置中心 / 检索调试 `/admin/retrieve`）。
- URL 路径保持不变；仅做代码层包隔离，每个文件头有 `# [用户侧接口]` / `# [运营后台 dashboard 接口]` 标记防混淆。
- `/retrieve` 裸检索调试接口已移入 dashboard 且由网关鉴权守护（本服务不再做角色判断），非用户侧接口。

## 5. 文件与提示词归属

- 文件维护在后台 admin 端（dashboard 包）；源文件存储抽象为 `FileProvider`，当前 `MinioFileProvider` 已实现，OSS 接入只需新增 `OssFileProvider` + `build_file_provider()` 分支，路由层零改动。
- 提示词在 Nacos 维护（`core/config_center/prompts_cache.py`），在后台 admin 端做审计（dashboard 的 config 中心，admin/operator 由网关下发，本服务不再内做角色校验）。

## 6. 本地基础设施 MCP 巡检

- `mcp_servers/` 目录：把本地 PostgreSQL / Redis / Milvus / MinIO / Nacos 封装为 MCP 工具，供 IDE/客户端 AI 助手巡检（按 `postgres_tools / redis_tools / milvus_tools / minio_tools / nacos_tools` 拆分，`server.py` 聚合）。注意目录不能叫 `mcp`（会与 mcp SDK 同名遮蔽），故用 `mcp_servers`。
- 仅用于本地开发/巡检，**不要**暴露到公网；`postgres_query` 可跑任意 SQL，需谨慎。
