> **使用说明**
> 1. 5 个场景**共用同一套技术底座**（RAG-Ultra 真实实现），差异只在业务叙事、语料类型与"租户"的定义。
> 2. 按目标公司的行业，挑最贴合的一个版本写进简历；其余场景可作为面试追问时的"迁移能力"佐证。
> 3. 文中**量化指标为示例口径**，请替换为你实际参与的真实数据（或按合理的量级微调），避免面试被追问具体口径时答不上来。
> 4. 技术细节均已锚定真实实现（组件名、算法、配置项均可在代码里指到），建议面试前能画出"FAQ 优先 → 意图分流 → 混合检索 → 重排 → 生成"的主链路。

## 0. 通用技术底座（5 个场景共用）

### 0.1 项目一句话定位
**RAG-Ultra**：面向多租户的企业级检索增强问答中台。以"**FAQ 优先 + RAG 兜底**"双通道为核心，融合混合检索、意图分流、多轮会话记忆与全链路治理，把散落的企业文档与标准问答沉淀为可溯源、可审计、可运营的知识服务能力。

### 0.2 技术栈（真实）

| 层次 | 技术 |
|---|---|
| 语言 / 框架 | Python 3.11 / FastAPI（uvicorn factory 多 worker）/ Pydantic / asyncio |
| 数据访问 | SQLAlchemy 2.0 async / MySQL 8（ORM 元数据）/ Redis 7 |
| 向量检索 | Milvus 2.x（dense cosine + sparse IP **双向量**，partition key 租户隔离）/ bge-m3（dense+sparse 一体）/ bge-reranker-v2-m3 / **RRF 融合** |
| 生成 / 编排 | LangChain LCEL / OpenAI 兼容 LLM 网关 / SSE 流式输出 |
| 意图 | BERT 意图分类器（通用知识 / 专业咨询二分类） |
| 服务治理 | Nacos 3.2（服务发现 + 配置中心；v3 OpenAPI 代理 + v2 gRPC 长连接） |
| 安全 | HMAC-SHA256 签名校验 + nonce（Redis SETNX）防重放 + 时间戳窗口 |
| 可观测 | trace_id 全链路透传 / API 调用日志落库 / `/admin/health` 探活 |
| 集成 | MCP（streamable-http，业务 API 自动封装为工具）/ MinIO·OSS 文件抽象 |
| 工程 | 分层架构 `app → core → store → common` / 启动 stage 编排 + 优雅降级 / pytest |

### 0.3 核心能力（对应真实实现，面试可展开）

- **FAQ 优先双通道**：先答案缓存 → 字面精确匹配 → BM25 相似 + 阈值 → 命中直接返回标准答案（**不调用 LLM，零成本、口径统一**）；未命中再走 RAG。
- **混合检索 + 精排**：dense + sparse 双路召回 → RRF 融合 → bge-reranker 重排；召回/精排条数由 `RECALL_K` / `RERANK_TOP_K` 统一控制。
- **两级切分索引**：语义父块 + 递归子块切分 → bge-m3 向量化 → Milvus 双向量落库（partition key 做租户隔离）。
- **意图分流**：通用知识 → 空上下文交 LLM 用自身知识直答；专业咨询 → LLM 四选一检索策略（**HyDE / 子查询 / 回溯问题 / 直接检索**），避免固定串行管道带来的冗余调用。
- **多轮会话与记忆**：服务端生成 `session_id`；Redis 存对话原文（TTL 30d）+ MySQL 注册表（可长期回看列表）；会话记忆 `summary + facts` 每 4 轮触发一次 compaction，注入生成上下文，弥补"只取最近 K 轮"的窗口限制。
- **上下文压缩（多级管线）**：检索片段超长时按大小（字符数）压缩——L0 按 rerank 分数截取 → L1 相关性精选 → L2 LLM 摘要合并；全程保留 `doc_name / page` 溯源引用，失败回退原样。
- **会话记录持久化**：每轮问答明细（query/answer/intent/chunks/model/tokens/latency）异步落库，不阻塞 SSE 主链路，支撑审计与质量分析。
- **质量评测**：接入 RAGAS 评测管道做 LLM 结果审计（faithfulness / answer relevance），不污染业务库。
- **多租户与身份**：`X-Tenant-Id` 租户隔离（Milvus partition key、Redis key 前缀、MySQL 按租户），`X-User-Id` 做会话级隔离；网关信任头 + HMAC 加固防直连伪造。
- **配置中心**：提示词与检索参数托管在 Nacos，**写操作走审批流**（申请 → 复核 → 执行 → 回滚/历史补偿），不直连写 Nacos。
- **文件与版本**：对象存储抽象（MinIO/OSS），get-or-create + 内容哈希去重 + 多版本 + 幂等上传，带租户归属校验防跨租户下载。
- **工程可靠性**：启动按 stage 编排（stage0 日志 → stage1 Redis/MySQL/Model/FileProvider 并发 → stage2 Milvus/FaqCache/NacosConfig → stage3 服务注册/索引消费/MCP），**单组件失败优雅降级不阻断启动**；`/admin/health` 供 Nacos 探活。
- **MCP 集成**：全部 HTTP API 自动封装为 MCP 工具（streamable-http），进程内 ASGI 复用同一套中间件与签名校验。

## 场景 1：半导体 / 高端制造 —— 设备运维知识中枢

### S · 项目背景
某晶圆制造 / 面板厂，产线设备类型众多（光刻、刻蚀、薄膜、量测），技术资料分散在 PLM、文件服务器与工程师个人电脑里：设备手册、报警代码表、维修 SOP、备件清单、历史工单各自为政。设备宕机按分钟计损失，现场工程师对"某个报警码历史上怎么处置"的检索效率直接决定 MTTR。

### T · 解决痛点
1. 手册动辄上千页、版本繁杂，人工翻查定位慢（平均 15–20 分钟/次）。
2. 报警码、维修 SOP、历史工单三者割裂，故障处置经验无法沉淀复用。
3. 新工程师上手周期长，依赖老师傅带教。
4. 多厂区 / 多产线既要知识隔离（工艺保密），又要复用通用排障经验。
5. 现场给出的处置建议必须**可溯源到手册条目**，不能凭模型臆造。

### A · 我的工作
- **双通道问答**：把高频报警码与标准处置沉淀为 FAQ 库，命中即直接返回标准答案（不调 LLM），保证口径统一与零推理成本；未命中的长尾故障走文档检索。
- **混合检索 + 精排**：手册/工单经语义父块 + 递归子块切分后由 bge-m3 生成 dense+sparse 双向量入 Milvus（按厂区 partition key 隔离）；双路召回 → RRF 融合 → bge-reranker 重排，解决"手册术语与现场口语表述不一致"的召回难题。
- **意图分流**：通用设备原理类问题走 LLM 直答；具体故障走专业咨询链路，由 LLM 在 HyDE / 子查询 / 回溯问题中四选一，显著提升多跳排障类问题的召回。
- **多轮与记忆**：现场追问（"这条报警上次是怎么处理的""那备件还有库存吗"）依赖会话记忆——每 4 轮 compaction 生成 `summary + facts` 注入上下文，突破"只取最近 K 轮"的限制。
- **长上下文处理**：手册片段拼接易超窗，实现多级上下文压缩（预算截断 → 相关性精选 → LLM 摘要），压缩后仍保留 `doc_name / page` 溯源，失败回退原样不阻断。
- **工程落地**：现场终端经 MCP 工具调用业务 API；多厂区多租户隔离 + HMAC 签名防直连；启动 stage 编排，模型/向量库单组件异常时优雅降级不影响整体可用性。

### R · 项目成果
- 故障处置建议平均获取时间由 **18 分钟降至 2 分钟内**，MTTR 下降约 **35%**。
- 覆盖 **8 类关键设备、1200+ 份手册与 3 万条历史工单**，问答首次可用率 **92%**。
- FAQ 优先通道承接约 **45%** 请求，直接省去 LLM 调用，月度推理成本下降 **40%**。
- 上下文压缩使长手册场景单次 prompt token 下降 **55%**，且 100% 回答可溯源到具体手册条目。

## 场景 2：电力 / 能源 —— 电网调度与检修安全规程问答

### S · 项目背景
省级电网及下属地市公司，调度运行、检修作业强依赖规程文件：《调度规程》《电力安全工作规程》《两票三制》实施细则、设备台账、典型操作票、历史缺陷记录。规程修订频繁、地区细则有差异，一线人员"查规程"是刚需，且任何错误引用都可能引发安全事故。

### T · 解决痛点
1. 规程文件层级多（国标/行标/省公司/地市细则），人工判断"该用哪一版"极易出错。
2. 操作票、安规条款检索慢，检修窗口期时间紧。
3. 行业强监管：回答必须可溯源、可审计，知识变更必须留痕、可回滚。
4. 多地市公司需租户隔离，且省公司要能统一运营标准问答。

### A · 我的工作
- **标准答案优先**：把安规条款、典型操作票、标准处置沉淀为 FAQ/标准问答库，命中即返回权威原文（不经过 LLM 改写），杜绝"模型发挥"导致的合规风险。
- **混合检索 + 版本感知**：规程文档两级切分入 Milvus（dense+sparse，partition key 按地市公司隔离），RRF 融合 + reranker 精排；回答附 `doc_name / page / 版本`，支持跨版本比对。
- **审批流驱动的知识运营**：提示词与检索阈值托管在 Nacos 配置中心，**任何变更走"申请 → 复核 → 执行 → 回滚"审批流**（含历史 nid 补偿同步），不直连写配置中心，满足"知识变更留痕可回滚"的监管要求。
- **全链路审计**：trace_id 全链路透传 + API 调用日志落库；每轮问答明细异步持久化（query/answer/引用条款/模型/耗时），支撑事后追责与质量抽查。
- **质量评测**：接入 RAGAS 评测管道做回答审计（faithfulness / answer relevance），形成"回答质量 → 知识库修订"闭环。
- **安全与高可用**：HMAC-SHA256 签名 + nonce 防重放 + 时间戳窗口，防绕过调度网关直连；`/admin/health` 供 Nacos 探活，组件异常优雅降级。

### R · 项目成果
- 规程条款检索由**人工 10 分钟降至秒级**，检修准备时长缩短 **30%**。
- 覆盖 **省/地市两级共 23 个租户、5000+ 份规程文件**，回答**100% 可溯源**到具体条款与版本。
- 知识变更审批流上线后，配置类变更**零误操作、全部可回滚**，通过公司合规审计。
- 会话持久化为 **12 万轮**问答建立审计档案，支撑季度质量抽查与责任追溯。

## 场景 3：航空 / 轨交 MRO —— 适航维修手册与技术通告问答

### S · 项目背景
航空维修企业（MRO）与轨道交通运维单位，维修作业严格依据 AMM/IPC/SRM 手册、适航指令（AD）、服务通告（SB）、工卡与历史故障库。手册与通告**版本生命周期复杂**（现行/作废/替代），维修人员按错版本施工会直接导致适航违规。

### T · 解决痛点
1. 手册与 SB/AD 版本多、替代关系复杂，人工确认"现行有效版本"成本高。
2. 维修排故需同时参考手册、工卡、历史相似故障，资料跨系统。
3. 适航监管要求任何技术依据可追溯到具体手册章节与通告编号。
4. 多机型、多维修基地、多客户（航司）需严格隔离又需共享通用排故经验。

### A · 我的工作
- **多版本文件治理**：对象存储抽象（MinIO/OSS）上实现 get-or-create + 内容哈希去重 + 版本历史 + 幂等上传，回答强制标注所依据的手册/通告**版本与章节**，过期版本触发提示。
- **双通道**：高频排故结论与标准工卡沉淀为 FAQ，命中直接返回；长尾故障走文档检索（手册 + 工卡 + 历史故障库）。
- **混合检索 + 精排**：手册长文档语义父块 + 递归子块切分，bge-m3 双向量入 Milvus（partition key 按机型/基地隔离）；RRF 融合 + reranker 精排，精准定位到章节级。
- **意图分流与策略选择**：机型原理类问题 LLM 直答；具体排故走专业链路，LLM 四选一（HyDE/子查询/回溯/直接），提升"多症状 → 单一故障源"类复杂排故的召回。
- **长文档处理**：手册章节拼接超窗，启用多级上下文压缩，保留章节溯源；失败回退原样。
- **工程与集成**：MCP 把业务 API 封装为工具，接入维修管理系统；启动 stage 编排 + 组件优雅降级；HMAC 签名防直连。

### R · 项目成果
- 排故技术依据获取时间由 **25 分钟降至 3 分钟**，单次定检准备工时下降 **28%**。
- 覆盖 **6 种机型、8000+ 份手册与 1.5 万条 SB/AD**，章节级溯源准确率 **96%**。

## 场景 4：生物医药 / 制药 —— 医学信息与注册申报资料问答

### S · 项目背景
制药企业医学信息（MedInfo）团队需响应医疗卫生专业人士（HCP）的产品问询，注册事务（RA）团队需基于 CTD 模块、SOP、临床试验文献准备申报资料。回答既要快速，又必须**严格限定在已批准的资料范围内**，任何超范围表述都可能构成合规风险。

### T · 解决痛点
1. 已批准的标准回复（FAQ）与原始文献/CTD 资料分散，人工比对耗时。
2. 回答必须限定在批准范围内，不能由模型自由发挥。
3. 申报资料检索跨 CTD 模块、SOP、文献，多跳查询多。
4. 不同治疗领域/产品线的资料需隔离，且回答需支持质量评测与审批留痕。

### A · 我的工作
- **合规优先的 FAQ 通道**：把已批准的标准医学回复沉淀为 FAQ，命中直接返回（不调 LLM），确保对外口径**严格一致且可审计**；未覆盖问题走资料检索并明确标注"依据来源"。
- **混合检索 + 精排**：CTD 模块、SOP、临床文献两级切分后 bge-m3 双向量入 Milvus（partition key 按治疗领域/产品线隔离）；RRF 融合 + reranker 精排，支撑跨模块多跳检索。

## 附：面试高频追问准备清单

| 追问 | 应答要点 |
|---|---|
| 为什么"FAQ 优先"而不是直接 RAG？ | 高频问题命中标准答案**不调 LLM**：零成本、零延迟、口径统一、可审计；长尾才走 RAG，成本与质量最优。 |
| 为什么用 dense + sparse 双向量？ | dense 抓语义（口语化表述），sparse 抓关键词/术语（型号、报警码、条款号），RRF 融合互补，实测召回明显优于单路。 |
| 为什么重排放在召回之后？ | 召回求全（高召回率）、重排求准（bge-reranker 交叉编码精排），`RECALL_K` / `RERANK_TOP_K` 分离控制，性价比最优。 |
| 为什么"四选一"而不是串行跑 HyDE+子查询+回溯？ | 串行至少多 1–2 次 LLM 调用，成本高、延迟高，且回溯与子查询方向互斥；由 LLM 选最合适的一种。 |
| 上下文压缩会不会丢信息？ | 多级管线：先免费的预算截断/相关性精选，只有超硬上限才启用付费的 LLM 摘要；全程保留 `doc_name/page` 溯源，异常回退原样。 |
| 多租户怎么保证不串数据？ | 租户维度：Milvus partition key + Redis key 前缀 + MySQL 按 tenant_id；用户维度：`X-User-Id` 隔离会话；网关信任头 + HMAC 签名防伪造。 |
| 组件挂了怎么办？ | 启动按 stage 编排，单组件失败**优雅降级不阻断启动**（如意图模型缺失降级为默认标签）；`/admin/health` 供 Nacos 探活摘除故障实例。 |
| 会话为什么 Redis + MySQL 双写？ | Redis 存对话原文（热路径低延迟 + TTL 自动清冷数据），MySQL 存会话注册表（可长期回看列表，不受 TTL 影响）。 |

## 场景 10：HR SaaS —— 员工政策自助问答（多租户企业服务）

### S · 项目背景
HR SaaS（人力资源共享服务中心 / HRSSC）为企业客户提供员工自助服务：员工查询假期、报销、社保公积金、考勤、绩效、劳动合同等政策。每家客户的制度文件不同（员工手册、各地区社保政策、报销标准），且政策随地区与时间变化。HR 每天被重复问题淹没。

### T · 解决痛点
1. **多租户数据隔离是生命线**：A 公司的制度绝不能出现在 B 公司员工的回答里。
2. 制度文件更新频繁（社保基数调整、报销标准变更），回答必须基于**现行版本**。
3. 政策类回答涉及劳动权益，必须口径准确、可追溯，错误回答可能引发劳动争议。
4. 各客户制度差异大，平台需支持客户自定义提示词与阈值，且变更可控。
5. 员工常多轮追问（"那年假没休完怎么折算"），需要上下文连贯。

### A · 我的工作
- **三层租户隔离**：`X-Tenant-Id` 企业租户维度——Milvus **partition key** 隔离向量、Redis **key 前缀**隔离缓存与会话、MySQL 按 `tenant_id` 隔离元数据；`X-User-Id` 做员工级会话隔离；网关信任头 + **HMAC-SHA256 签名 + nonce SETNX 防重放**防绕过网关直连伪造身份。
- **制度原文优先**：把各客户员工手册条款、报销 / 假期 / 社保标准沉淀为 FAQ，命中即返回**制度原文**（不调 LLM），保证对外口径与 HR 书面制度完全一致；长尾走制度文件检索。
- **混合检索 + 精排**：制度文件两级切分后 bge-m3 双向量入 Milvus（按企业 partition key 隔离）；RRF 融合 + reranker 精排；`RECALL_K` / `RERANK_TOP_K` 统一控制，兼顾准确与成本。
- **客户级可配置 + 审批流**：提示词与检索阈值托管 Nacos，**按租户隔离配置**；客户侧变更走"申请 → 复核 → 执行 → 回滚"审批流并留痕，支持按历史 nid 回滚，避免误改影响全员。
- **版本与审计**：制度文件版本治理，回答标注所依据的**制度版本与生效日期**；trace_id 透传 + API 日志落库 + 每轮问答明细异步持久化，形成**可举证的问答档案**（劳动争议时可调取"当时系统给出的口径"）。
- **多轮与工程**：员工追问依赖会话记忆（4 轮 compaction 生成 `summary + facts`）；接入 RAGAS 做 faithfulness 评测闭环；启动 stage 编排 + 组件优雅降级，保障高峰期可用。

### R · 项目成果
- HR 重复咨询量下降 **58%**，员工政策问题平均自助解决时长 **< 1 分钟**。
- 支撑 **1200+ 家企业客户**接入（同一套底层、各客户制度隔离），隔离相关**零数据串扰事故**。
- 制度版本治理 + 审计档案上线后，政策类回答**100% 可举证**，显著提升劳动争议举证效率。
- RAGAS 评测闭环使回答忠实度由 0.74 提升至 **0.91**；FAQ 优先通道承接 **52%** 请求，平台推理成本下降 **43%**。
