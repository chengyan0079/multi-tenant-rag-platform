# 面向多租户的检索增强问答 面试准备（RAG 技术向）

> 这份文档只聚焦 RAG 本身的技术链路：索引切片、向量化、混合检索、重排、查询增强、FAQ 优先、生成、上下文压缩、多轮记忆、多租户检索隔离与评测。
> 鉴权、项目演进、文档说明类内容不在此列。
> 题目有粗有细，答案按当前代码实现来讲，口语化、少铺垫。

---

## 一、项目介绍（按 STAR 准备，可直接背）

> 面试讲项目别上来就堆技术，按 STAR 讲：背景（Situation）→ 痛点/任务（Task）→ 技术动作（Action）→ 成果（Result）。下面四段对着用。

**【S 背景】** 我做的是一个面向多租户的检索增强问答中台，落地在企业的知识服务场景。企业里资料其实不少，但散在共享盘、OA、邮件里，格式还乱。

**【T 痛点/任务】** 一线员工要找个条款得翻半天，找到一个还不敢确定是不是现行版本；很多经验只活在老员工脑子里，人一走就断片。直接把文档丢给大模型也不行——长尾检索、口径不统一、缺审计、没有租户隔离，进不了生产。我接到的任务就是把这些散落文档和经验变成"问一句就能拿到带出处答案"的服务，且要具备进生产的条件。

**【A 技术动作】** 核心链路做成"FAQ 优先 + RAG 兜底"：高频问题命中标准答案直接返回、不调大模型，长尾才走检索增强。检索上用 bge-m3 的 dense + sparse 双向量做混合召回，RRF 融合后再用 bge-reranker 交叉编码重排；切片用父块/子块两级结构，子块检索、父块当上下文。生成侧用 LangChain LCEL 组装结果、SSE 流式输出。工程上补齐了多租户三层隔离（Milvus partition key、Redis key 前缀、PostgreSQL tenant_id）、Nacos 配置中心和审批流、按 stage 编排的启动与优雅降级，以及全链路 trace_id 透传和 API 日志落库做审计。技术栈是 FastAPI + PostgreSQL + Milvus + Redis + Nacos + MCP。

**【R 成果】** 高频问答做到了零推理成本、口径统一；长尾问题能通过带出处的答案溯源定责；多租户数据不串、配置变更可回滚、单组件故障只降级不阻断，整体达到了能进生产的工程水位。后续还在补增量索引、RAGAS 评测和运营前端这些厚度。

> 一句话串版（临场救急）："一个面向多租户的企业知识问答中台，解决资料找不到、不敢用、经验留不住的痛点，用 FAQ 优先 + 混合检索重排的 RAG 链路落地，技术栈 FastAPI/Milvus/Redis/Nacos，做到了带出处溯源、多租户隔离和生产级降级。"

## 二、面试题

### （一）索引与切片（写入侧）

**Q1. 文档切分为什么要用"父块/子块"两级结构？**

答：一句话——子块负责检索精度，父块负责生成语境。子块切得小，检索时能精准定位到具体那一句，召回更准；但真要拿去生成答案，光给那一小句大模型缺上下文，容易答飘。所以我让子块在 metadata 里带上 `parent_id` 和 `parent_content`，检索命中子块后回退到它所属的父块当上下文喂给模型。

切片流程是：先用 BGE 语义切分（按语义边界断）出父块，再在父块内部用递归字符切分出子块。这样既保证检索粒度细，又保证生成时语义完整。

**Q2. 语义切分具体怎么做的，为什么不直接按字数切？**

答：用的是基于 BGE-M3 向量的 `SemanticChunker`（LangChain 那个）。它不是按固定字符数硬切，而是先对句子做向量化，看相邻句子的向量距离，距离突然变大（语义跳变）的地方就是断点，threshold 用的是 percentile 类型、amount 设 95。再配一个句子级正则 `(?<=[。！？\n])`，保证不会把一个长句从中劈开。

相比按字数切，语义切分能尽量让一个块表达一个完整意思，检索时块内语义更一致，召回质量更稳。代价是多一次向量推理，所以只在切父块时用，子块还是用轻量的递归字符切分。

**Q3. 索引怎么保证幂等、重复跑不串数据？**

答：chunk_id 由 `(tenant_id, doc_id, parent_id, seq)` 稳定生成，落到 Milvus 里走 upsert，所以同一份文档重跑索引是覆盖而不是新增。文档本身用"路径 + 正文前 200 字符"的 md5 短哈希做前缀 ID，内容哈希去重、版本可追。这是写入侧幂等的关键，也是后续做版本治理和异步重索引的基础。

### （二）向量化

**Q4. 为什么选 bge-m3，dense 和 sparse 两路各自解决什么问题？**

答：bge-m3 一个模型同时产出 dense 向量和 sparse 向量，一次推理拿两路，省事。dense 是语义向量，解决"用户口语和文档书面术语对不上"的问题——比如用户问"机器报警了咋办"，文档写的是"设备触发故障码处理流程"，字面没关系但语义近，dense 能捞回来。sparse 是词面稀疏向量（类似 BM25 那一类），解决型号、条款号、报警码这种要字面精确命中的查询，纯语义向量遇到这种反而容易漂。两路互补，所以才做混合检索。

**Q5. 混合检索之后为什么要再重排，光融合不够吗？**

答：融合（RRF）只是把两路召回的排名合并，它看的是"谁排得靠前"，并不真正理解 query 和片段的相关性。rerank 用 bge-reranker 这种交叉编码器，把 query 和每个候选片段拼一起过一遍模型，直接打一个相关性分数，精排质量明显更高。所以它放在融合之后，作为"精排"那一步。融合解决召回广度和融合，重排解决精排准度，两步各有分工。

### （三）检索与融合

**Q6. RRF 和加权融合（WeightedRanker）你选了哪个，为什么？**

答：默认用 RRF（Reciprocal Rank Fusion），代码里两种都支持，参数一切就行。我选 RRF 主要是它不依赖两路分数在同一量纲——dense 的 cosine 和 sparse 的 IP 分数尺度根本不一样，加权的话权重得反复调、还容易过拟合某批数据。RRF 只看排名：每个文档得分是各召回列表里 `1/(k+rank)` 的累加，k 是平滑常数，跟原始分数绝对值无关，省心也稳。加权融合更适合你明确知道某路该占多少权重、且分数可比较的场景。

**Q7. 同一父块下多个子块都命中了，你怎么去重和定位？**

答：retriever 里有一步按 `parent_id` 去重，同一父块只返回一次。但命中了哪些具体子块不能丢，所以把命中的子块内容在父块原文里用 `<检索定位区块>` 标签标出来，而不是把整段父块重复贴好几遍。这样既保证上下文完整，又让前端知道答案落在父块哪几段，方便高亮和溯源。

**Q8. 重排失败了你怎么处理？**

答：降级，退回只用 RRF 融合的结果，不抛错、不阻断。`model.reranker` 为空或者重排调用抛异常，都 catch 住打条 warning，直接拿融合后的父块返回。生产上 reranker 是额外的交叉编码模型，加载或推理偶尔出问题，不能因为它挂了就让用户拿不到答案，所以把它当"锦上添花"而不是"必经关卡"。

### （四）查询增强与路由策略

**Q9. 检索增强策略"四选一"具体哪四种，代码里怎么落地的？**

答：在"专业咨询"分支里，用 LLM 零样本分类从四种里选一种：
- 直接检索（DIRECT）：原问题直接去查；
- HyDE（假设性文档嵌入）：先让模型编一段假设答案，用这段假设答案去检索，缓解语义落差；
- 子查询（SUB_QUERY）：把复杂问题拆成几个子问题，分别检索后合并去重；
- 回溯（BACKTRACK）：把绕来绕去的长问题抽象成核心问题再查。

代码里 `QueryAugmenter` 每种策略对应一个 `retrieve_*` 方法，HyDE/子查询/回溯都是先调 LLM 生成改写结果，再用改写后的 query 去检索；子查询是多路结果按 `chunk_id`（无 id 按内容）合并去重、截断到 `RERANK_TOP_K`。选哪种由 `StrategySelector` 用 temperature=0 跑一句短分类决定。

**Q10. 为什么是"四选一"而不是把四种改写都试一遍再融合？**

答：串着试成本太高、延迟也压不住——每加一种改写就多一轮 LLM 调用加一轮检索，四种全跑对长尾问题太奢侈。四选一让每次查询只多一次轻量分类调用，选定一种再增强，性价比更合适。这是当时明确定的取舍，不是技术做不到，是投入产出怎么算的问题。

**Q11. 高级策略检索为空时怎么办？**

答：自动回退到 DIRECT 直接检索，保证检索结果不为空。`augment_and_retrieve` 里任意增强策略返回空，且当前不是 DIRECT，就再跑一次原问题检索。另外 HyDE/子查询/回溯在生成改写结果失败或结果为空时，也会各自内部回退 DIRECT。层层兜底，核心目标是"检索不能空"。

**Q12. 通用知识和专业咨询为什么分流，处理差别在哪？**

答：意图识别用轻量 BERT 分类。通用知识（比如"帮我写个周报模板"）根本不进检索，直接空上下文丢给大模型用自身知识答，不会因为知识库没命中就拒答。专业咨询才走上面那套检索增强。分流的好处是通用闲聊/创作类请求不浪费检索资源，也避免硬塞检索噪声把答案带偏。

### （五）FAQ 优先

**Q13. "FAQ 优先"具体指什么，为什么能省成本又稳口径？**

答：用户问一句，先去 FAQ 标准库找现成答案。匹配是先字面精确比对，再 BM25 相似度比对，超过阈值就直接返回标准答案，整条链路不调大模型。企业里高频问题就那么些，每天可能被问几百次，每次让 LLM 现编既慢又贵、还口径不统一；FAQ 命中零推理成本，答案还是运营配的权威原文，合规上最稳。所以它排在答案缓存之后、意图识别和 RAG 之前，命中即返回。

**Q14. FAQ 命中后还回写答案缓存吗？**

答：回写。`router` 里 FAQ 命中后会 `set_answer` 把答案按 `(tenant_id, query)` 写进 Redis，下次同样问题连 FAQ 库都跳过、直接命中答案缓存。缓存命中在最前面，FAQ 命中在中间，两者都是"不调大模型"的快路径，RAG 是最后的兜底。

### （六）生成与多轮

**Q15. 生成侧是怎么组织的，流式怎么实现？**

答：生成用 LangChain LCEL 把检索结果组装成 prompt 再调大模型，`generator` 同时提供 `generate`（整段）和 `astream`（逐 token）。问答主流程 `answer` / `answer_stream` 共用同一条链路，只是输出协议不同：流式时逐 token 推 `("token", 文本)`，结束推 `("done", {})`，前面还会先推一个 `("meta", ...)` 把 source、召回片段、压缩方式带出去，方便前端先渲染来源再流式出字。

**Q16. 多轮对话的上下文和记忆怎么管？**

答：会话原文放 Redis 带 TTL，过期自动清；想要长期回看的注册表落 PostgreSQL。记忆这块每 4 轮做一次 compaction，生成 `summary` 和 `facts` 注入后续生成上下文，避免上下文越滚越长撑爆窗口。光存原文不够，得把前面几轮关键信息压成摘要持续喂给模型，否则跨窗口追问会断片。

**Q17. 问答明细落库失败会影响用户拿到答案吗？**

答：不会。落库是异步最佳努力（best-effort），`_persist_session` 把写协程丢后台，并发超上限直接丢弃并告警，不排队拖慢主链路。明细本质是审计/统计数据，丢一轮比拖慢响应划算；写失败也被 catch 住只告警，绝不抛回主流程。

### （七）上下文压缩

**Q18. 检索回来的片段太长塞不进上下文窗口，你怎么处理？**

答：有一套多级压缩管线，定位是兜底——只在 chunks 自身就让 prompt 超窗时才动手，多轮常规裁剪不在这里。三级：
- L0 按字符数截取，单片段超 `COMPRESS_MAX_CHUNK_CHARS` 按句截断，再按总预算 `COMPRESS_MAX_TOTAL_CHARS` 累加保留高分片段；
- L1 相关性精选，按 rerank 分数丢低分片段（阈值 `COMPRESS_SIM_THRESHOLD`）；
- L2 LLM 摘要合并（付费，默认关），把保留片段压成一段摘要，溯源字段汇总所有被合并来源。

任何一步异常都回退原样、不抛主链路。还有个细节：既没丢片段也没截短时记为 `none`，否则"压缩触发率"这个观测指标会虚高到 100%，失去意义。

### （八）多租户检索隔离（RAG 服务侧）

**Q19. 多租户下检索怎么保证不串数据？**

答：向量层用 Milvus 的 partition key 做租户隔离，混合检索时把 `tenant_id` 当过滤条件直接带进查询表达式，检索范围天然限定在当前租户。再叠加 Redis 的 key 前缀隔离和 PostgreSQL 的 `tenant_id` 字段隔离，三层各管一段。检索链路本身不直接拼 SQL，tenant_id 由接入层解析后透传到 retriever，retriever 再传给 Milvus 的 filter。

### （九）评测与质量（诚实说短板）

**Q20. 怎么验证你的检索/生成效果好不好？**

答：靠 RAGAS 评测管道，指标主要盯四个，参考 rag-pro 项目的落地写法：
- **Faithfulness（忠实度）**：答案里每个陈述句能不能在检索上下文里找到依据，找到的句数 ÷ 答案总陈述句数。直接对应"幻觉"问题——分数低就是模型在凭空编。
- **Answer Relevancy（答案相关性）**：让 LLM 从答案反推几个问题，看这些反推问题和用户原问题的向量相似度。回答偏题、啰嗦会拉低这分。
- **Context Precision（上下文精确度）**：召回的片段里真正有用的占多大比例，惩罚"召回了一堆但九成是噪声"。
- **Context Recall（上下文召回率）**：标准答案里的信息点，有多少能在召回上下文里找到，看检索漏没漏关键内容。

实现上（rag-pro 的 `rag_as.py`）用 `ragas.experiment` 装饰器把评测函数包成"实验算子"，四个 metric 用 `asyncio.gather` 并发打分，方便对不同模型/prompt/检索策略横向对比。当前项目这层还在补，但 `rag_turn` 明细已经把 strategy/chunks/source/压缩方式落了，等于把"取数"先备好，接 RAGAS 时直接喂 `user_input / response / retrieved_contexts / reference` 就行。

### （十）开放题

**Q21. 如果让你现在加一个"异步索引 Worker"，你会怎么设计？**

答：现在索引是同步链路（加载→父子块切分→写 PG→向量化→upsert Milvus）。我倾向用任务队列（Celery 或 ARQ）把"建索引"变异步任务：文档上传先落库、状态置"索引中"，Worker 消费后跑切片和向量化，跑完回写状态，失败有重试和幂等（chunk_id 四元组保证 upsert 覆盖）。状态机能让运营后台查"文档索引到哪了"，也避免大文件把请求线程卡死。这正是当前列在最高优先级的高优先项。

**Q22. 你这个项目里最值得讲的一个 RAG 技术决策是什么？**

答：我会讲"四选一 vs 串联"那个，或者"FAQ 不调 LLM"的成本分层。前者是检索增强的性价比权衡——串着试四种改写成本压不住，改成 LLM 一次选一种；后者是把高频问题从生成链路里摘出来，直接决定系统成本和口径稳定性。两个都是"不是技术能不能做，而是投入产出怎么算"的决策，比单纯堆模型更有得聊。

**Q23. 召回和精排的条数你是怎么定的，为什么不让请求自己传 top_k？**

答：召回候选数 `RECALL_K` 和精排保留数 `RERANK_TOP_K` 都是配置项统一控制，不按请求传。原因是这两者对检索质量和延迟的影响要整体调，交给调用方传容易把系统调坏，也不利于统一观测和压测。检索只负责"召回→融合→重排→压缩"，条数这类策略参数集中在一处，改起来可控。

### （十一）RAG 工程生产扩展（项目未必实现，但企业级必问）

> 这一节不局限于本项目当前代码，而是企业里真把 RAG 跑起来后会撞上的工程问题。面试时讲清楚"理想做法 + 本项目现状"会很加分。

**Q24. 文档频繁更新，知识库怎么保持时效？**

答：核心是增量索引 + 版本治理。理想做法是：每个文档用内容哈希或版本号管理，变更只重索引受影响的 chunk（而不是全量重建），旧版本标记失效但不立刻物理删，方便回滚和审计。我们项目里 chunk_id 用 `(tenant_id, doc_id, parent_id, seq)` 做 upsert 幂等，重跑能覆盖，但"增量 diff + 版本历史 + 失效标记"这套完整的版本治理还停留在设计阶段，目前更偏全量重建思路。生产上如果文档每天大批变，全量重建扛不住，一定得做增量。

**Q25. 检索召回率低、经常答非所问，怎么系统排查？**

答：分三层查。先看召回层：是不是 chunk 切太大/太小、是不是只用了语义向量丢了字面精确查询（所以要做混合检索）、query 是不是需要改写（我们项目有 HyDE/子查询/回溯四种策略就是干这个的）。再看融合重排层：RRF 的 k、rerank 阈值合不合理，低分片段有没有被带进来。最后看生成层：是不是检索到了但被上下文压缩误删了（所以压缩要保留溯源、别乱丢）。排查时建一个 bad case 库，每条记录 query、召回片段、最终答案，才能定位是哪一环掉链子。

**Q26. 大模型幻觉、答案不可信，生产上怎么缓解？**

答：几招叠着用。第一，强制带出处（citation），答案里标注来自哪个文档哪页，让用户能核对，我们项目 chunks 一直带 `doc_name`/`page` 就是为这个。第二，约束生成：prompt 里明确要求"只依据给定资料，资料没有就回答不知道"，别让模型自由发挥。第三，置信度/拒答机制：检索分数太低或没命中就走"未找到"而不是硬编。第四，关键场景加人工复核或后置校验。幻觉不可能彻底消灭，但能让它"可被发现的、可追责的"。

**Q27. 长文档、超长上下文怎么处理？**

答：两件事。一个是切片策略——长文档用语义切分保块内完整，配合父块/子块保上下文，我们项目这套是现成的。另一个是上下文压缩——检索回太多片段塞不进窗口时，按相关性精选、必要时摘要合并（我们有 L0/L1/L2 三级压缩）。更往前一步，生产上还会做"查询聚焦"，先让模型从长文档里定位相关段落再细读，或者分层检索（先粗召回章节、再精召回段落）。核心原则：别把整本文档硬塞，按需取、按需压。

**Q28. 首字延迟和并发性能怎么优化？**

答：首字延迟主要卡在检索 + 重排 + 模型首 token。优化点：embedding 和 rerank 模型本地部署、批处理；检索走向量库近实时索引；答案缓存命中直接返回（我们项目答案缓存前置就是为这个）；流式输出把"首字"和"完整"解耦，用户先看到字就不觉得慢。并发上：模型推理是瓶颈，要么限流排队，要么把 embedding/rerank/LLM 拆成独立推理服务横向扩，多进程重复加载模型的内存问题也得靠这个解决。

**Q29. 成本怎么控？**

答：大头是 embedding 和 LLM 调用。embedding 可以缓存（同一 query 同一租户不重复算），我们项目答案缓存已经顺带覆盖了一部分。LLM 上：高频问题走 FAQ 优先不调模型（零成本），通用知识用便宜小模型，只有专业咨询才走重模型；长文本摘要合并默认关，能不调就不调。再就是模型选型分层，别所有请求都砸最贵那个。成本这块本质是"路由分层 + 缓存 + 模型分级"三件套。

**Q30. 多轮对话上下文膨胀怎么管？**

答：不能无脑把历史全塞进 prompt。常见做法：滑动窗口只保留最近 N 轮、或用向量检索从历史里挑相关的、或定期 compaction 压缩成摘要。我们项目是每 4 轮做 compaction 生成 summary + facts 注入，避免窗口撑爆。再往前还有"对话级缓存"和"关键信息抽取"，把用户偏好、已确认事实单独存，不每次都重传全文。

**Q31. 评测体系怎么建？**

答：离线和线上两套。线上埋点统计 FAQ 命中率、缓存命中率、检索有命中但答非所问占比、用户 thumbs down 率——这套我们 `rag_turn` 明细已经能支撑。离线评测靠 RAGAS，参考 rag-pro 的落地：

一是**测试集怎么来**。冷启动没标注数据时，用 RAGAS 的 `TestsetGenerator`（喂原始文档，LLM 自动"切分→生成问题→生成答案"）先造一批冒烟测试集；上线后从审计日志挑 Bad Case 人工修正打标，沉淀成"黄金测试集"做严格回归。

二是**指标怎么算**。上面 Q20 那四个指标，`user_input / response / retrieved_contexts` 配上 `reference`（标准答案）就能跑；需要 reference 的指标（context recall / precision）靠黄金集，不需要的（faithfulness / answer relevancy）上线初期就能直接跑。

三是**评测怎么工程化**。`ragas.experiment` 把每个评测变体包成算子，模型和 prompt、检索策略都能横向 A/B，结果落 JSON 方便比。RAGAS 依赖（ragas / langchain-community）单独建环境跑，不进生产 `requirements.txt`，避免依赖冲突。

我们项目 RAGAS 这层还在补，但取数和指标口径已经对齐了。

**Q32. 向量库规模上来后，性能和可靠性怎么保证？**

答：Milvus 这类向量库，规模大了要考虑：分区/partition key 做数据隔离和裁剪（我们项目按租户 partition，检索天然缩小范围）；索引类型选对（IVF、HNSW 在召回率和延迟上权衡）；副本和负载均衡扛读压力；近实时索引避免每次写都重建。可靠性上要有健康探活（我们 `/admin/health` 报组件状态）、故障实例摘除、以及检索依赖挂了能降级（rerank 失败退回 RRF 就是例子）。

**Q33. 文档解析质量（PDF/表格/OCR）怎么保证？**

答：这是 RAG 质量的隐形天花板——检索再好，文档本身解析成乱码或丢表格，后面全白搭。生产要覆盖多格式加载器（pdf/docx/pptx/图片），PDF 文本层缺失得上 OCR，表格要专门抽取不能当纯文本。还要做解析后清洗：去页眉页脚噪声、合并被分页切断的段落。我们项目有 `document_loaders` 目录做多格式加载，但 OCR 和表格精细化抽取这块目前还不如成熟方案，算是要补的厚度。

**Q34. 数据安全和合规（租户数据不出域、脱敏、权限）怎么处理？**

答：租户隔离是底线——我们项目三层隔离（Milvus partition key、Redis key 前缀、PG tenant_id）保证数据不串。再往上：敏感字段脱敏（PII 识别后打码或替换）、权限控制（谁能查哪个知识库）、审计留痕（谁问了什么、答案依据哪份文档，可追溯可定责）。合规场景还要求模型调用不出内网、数据不落第三方，这些靠私有化部署和网关管控解决。

**Q35. 冷启动：没多少标注数据时怎么上线？**

答：别等数据齐了再上。先用 FAQ 优先撑起高频问题（运营人工配一批标准问答，成本最低、最稳）；RAG 部分先用少量真实文档建库跑通链路，边用边补。检索策略和阈值初期可以先用经验值，靠线上 bad case 慢慢调。重点是先让"问一句有出处答案"跑起来，再迭代质量，而不是追求一上线就完美。

**Q36. 灰度发布和回滚怎么做？**

答：检索/生成相关的改动（切分参数、prompt、重排阈值、模型版本）风险高，不能全量一把梭。做法：按租户或小流量灰度，新配置和旧配置并行比对效果；prompt 和阈值这类我们项目已经托管到 Nacos 配置中心，并设计了"申请-复核-执行-回滚"审批流，改坏了能按历史版本回滚（Nacos 3.x 没 rollback 端点，实际是用历史 nid 取内容重发）。模型版本切换更要留 A/B 对照，别直接覆盖。

### （十二）意图识别模型训练

> 我们项目里意图识别是轻量 BERT 分类（通用知识 vs 专业咨询分流），这层如果面试官往"模型怎么训出来"深挖，下面三题能接住。

**Q37. 意图识别用的轻量 BERT 分类模型，你是怎么训练出来的？**

答：本质是文本多分类。底座选中文预训练的小模型（如 `bert-base-chinese` 或 RoBERTa-wwm 这类，参数量小、推理快，适合放接入层实时判）。流程：拿业务语料在预训练底座上做**下游微调（fine-tune）**——把 query 过 encoder 拿 `[CLS]` 向量，接一个分类头（几层 MLP）输出各意图类别概率，用交叉熵损失训。相比从零训，fine-tune 只需少量标注就能把通用语义适配到我们的意图分布上。训练框架用 HuggingFace `transformers` 的 `Trainer`，配合早停和学习率 warmup 防过拟合。

**Q38. 训练数据从哪来，正负样本怎么构造？**

答：三类来源。一是**线上日志挖掘**：FAQ 库里的人工标准问答天然是"专业咨询"正样本；通用知识类（写周报、闲聊）从对话日志里挑。二是**FAQ 反向生成**：用 LLM 拿 FAQ 标准问扩写同义问法，扩充专业类样本。三是**弱标注 + 人工校验**：先规则/关键词粗标一批，再抽样人工订正。负样本不用特意造——多分类里"非该类"的样本本身就是其他类的正样本，关键是各类别**分布要贴近线上真实流量**，别让模型训成偏科。数据还会留一份带版本号的训练集，模型重训可追溯。

**Q39. 模型上线后效果衰减、误分类怎么处理，怎么持续迭代？**

答：误分类的后果我们已经设计了兜底——通用知识误判成专业咨询顶多走一遍检索（多花点检索资源），专业咨询误判成通用知识会"答非所问"，所以后者是重点防的。迭代上：① 线上把"意图标签 + 最终用户是否 thumbs down / 是否转人工"落库，定期捞误判样本进训练集重训；② 分类置信度低时走"保守路由"——宁可进检索也别直接拒答，或触发二次澄清；③ 模型版本托管到 Nacos，和 prompt 一样能灰度 + 回滚。整体是"日志回流 → 标注 → 重训 → 灰度"的小闭环，不需要一次性标很多。

### （十三）RAG 整体流程（把链路串一遍）

> 面试官常让你"从头到尾讲一遍"，或者"哪个环节挂了怎么降级"。这两题练串讲和全局可靠性。

**Q40. 把你整个 RAG 链路从头到尾串一遍（用户问一句到你拿到带出处答案）？**

答：一句话版——`接入解析 → 答案缓存 → FAQ 优先 → 意图识别路由 → 查询增强 → 混合检索 → RRF 融合 → 重排 → 上下文压缩 → 生成（流式）→ 审计落库`，多租户三层隔离贯穿全程。

展开：① 接入层解析 `tenant_id`、生成 `trace_id`；② 先查答案缓存（命中直接返，零成本）；③ 命中 FAQ 标准库也直接返（不调 LLM）；④ 意图识别：通用知识分流走"空上下文 + 小模型直答"，专业咨询进检索；⑤ 专业分支里 LLM 四选一选查询增强策略（DIRECT/HyDE/子查询/回溯），增强后去检索；⑥ 检索用 bge-m3 出 dense+sparse 双向量，Milvus 按 `tenant_id` 过滤做混合召回；⑦ RRF 融合两路排名；⑧ bge-reranker 交叉编码精排；⑨ 命中子块按 `parent_id` 去重回退父块，超窗走 L0/L1/L2 压缩；⑩ 检索结果组装 prompt，LCEL 调模型，SSE 逐 token 推（先 meta 带 source、再 token、再 done）；⑪ 全链路 `rag_turn` 明细异步落库做审计。

**Q41. 各个环节出问题分别怎么降级，整条链路可靠性怎么保证？**

答：按环节讲降级：
- **FAQ / 缓存查不到**：正常往下走，不是故障。
- **意图识别模型挂了**：降级成默认进专业咨询检索（宁可多检索也不漏答），或走 DIRECT。
- **embedding 失败**：检索层整体降级提示，但缓存/FAQ 快路径仍在，高频问题不受影响。
- **rerank 失败**：catch 住，退回仅 RRF 融合结果，不抛错。
- **高级增强策略检索为空**：自动回退 DIRECT，保证检索不为空。
- **LLM 生成失败**：流式推错误事件，前端展示兜底话术。

可靠性靠三件事：① 每个外部依赖（Milvus/Redis/PG/模型）都健康探活，挂了只降级不阻断；② 所有"锦上添花"步骤（rerank、压缩、增强）都包 try/catch 回退，主链路（缓存→FAQ→检索→生成）尽量不依赖它们；③ 多租户隔离 + 全链路 `trace_id`，出问题能按租户、按 trace 定位。整体水位是"单组件故障只降质不阻断"。

## 三、容易被追问的代码细节（防备一下）

- **`RRFRanker(k=config.RRF_K)` 的 k**：平滑常数，防止排名靠前的文档分数被 `1/rank` 放得过大。
- **chunk_id 四元组**：`(tenant_id, doc_id, parent_id, seq)`，稳定且 upsert 幂等覆盖，重跑索引不重复建数据。
- **`_dedup_parent_with_highlight`**：按 `parent_id`（空则按整段内容）去重，命中子块用 `<检索定位区块>` 标签在父块内标出。
- **压缩的 method 取值**：`none` / `truncate` / `select` / `llm_summary`，结果带 `chars_before/after`、`dropped`，前端能知道实际压缩了多少、丢了几个片段。
- **会话记忆 compaction 间隔**：每 4 轮触发一次，生成 summary + facts 注入上下文。
- **流式事件协议**：meta（阶段信息）/ answer（整段，缓存或 FAQ）/ token（RAG 逐 token）/ done，靠 SSE 推。
- **检索条数来源**：`RECALL_K`（融合候选）/ `RERANK_TOP_K`（精排保留），由 config 统一控制，不按请求传。
