## 1. 背景与问题

### 1.1 单次检索：chunks 侧超长
检索召回的 `chunks` 经 rerank 后拼接进 prompt，可能：
- **超长**：内容累计过大，撑爆模型上下文窗口（多片段/长文档）；
- **噪声**：低相关片段稀释关键证据；
- **高成本**：冗余内容推高 LLM 调用费用与延迟。

### 1.2 多轮会话：记忆 + 历史 + chunks 三者叠加
多轮时 prompt 同时塞入**会话记忆**（`summary + facts`）、**历史对话**（最近若干条）与**本次检索 chunks**，风险更隐蔽：
- 三者**无总额度控制**，长会话下一起挤爆窗口；
- 记忆是历史对话的压缩摘要，与历史**内容冗余**，同一信息放两遍；
- 记忆拼进了「当前问题」标签下（见 §2.1），存在**语义错位**；
- 记忆里的历史结论与本次检索到的现行文档**冲突时无仲裁**；
- 用户多轮常用「它 / 那个方案」等指代词，依赖历史窗口与记忆消解。

## 2. 现状：当前 prompt 是怎么拼的（代码实证）

### 2.1 装配位置 `core/rag_generator/generator.py`

```python
# generator.py:105-111
question = query
if memory_text:
    question = f"{memory_text}\n\n{question}"          # 记忆拼进 question
if history:
    ctx = "\n".join(f"{h['role']}: {h['content']}" for h in history)
    question = f"历史对话:\n{ctx}\n\n当前问题: {question}"   # 历史再包一层
```

- `context` = 检索片段：`format_docs(to_documents(x["chunks"]))`（`generator.py:82`）；
- `history` = `conv_store.get_history(user_id, session_id)`，默认 `last=6`（`store/session_store.py:88`，`lrange(key, -6, -1)`），**条数写死在默认值、不可配**；
- `memory_text` = `MemoryService.build_injection_text(memory)`，即 `summary + facts`，**无长度上限**；
- 提示词模板由 Nacos 配置中心 `CORE_RAG_TEMPLATE` 提供（`RAGPromptsManager` 先 Redis 再 Nacos），兜底模板为 `"{context}\n\n用户问题：{question}"`。

### 2.2 由此确认的四个问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | 记忆拼进 `question`，被包进「当前问题:」标签 | 模型可能把记忆当成"用户刚说的话"，而非背景知识 |
| 2 | 记忆与历史冗余 | 同一信息两遍，白占额度 |
| 3 | 三者无额度叠加（chunks 压缩当前为 no-op、history 固定 6 条、memory 无上限） | 长会话挤爆窗口 |
| 4 | 记忆/历史结论与本次检索文档冲突时无仲裁 | 用旧结论回答新问题 |

## 3. 目标与设计原则

**目标**
1. 单次检索：按**配置的大小上限**控制 chunks 体积（兜底）。
2. 多轮会话：按**分层配额**装配记忆与历史，保证 chunks 证据不被牺牲。
3. 全程**保留来源溯源**（`doc_name / page`），可解释、可审计。
4. 配置驱动、可观测、**失败回退原样**，不阻断主链路。

**原则**
- **证据优先**：回答当前问题靠的是本次检索 chunks，其优先级与 system/query 同级。
- **零成本优先**：能用截取/去重解决的，不调用 LLM。
- **可降级**：压缩失败回退原样并告警。

---

## 4. 多轮上下文装配规范（核心）

### 4.1 分层配额与优先级

| 层级 | 内容 | 可否裁剪 | 说明 |
|---|---|---|---|
| **P0 不可动** | system 指令、当前 query、**本次检索 chunks** | ✗ | chunks 是回答当前问题的直接依据，**不因记忆/历史而牺牲** |
| **P2 可截取** | 最近历史对话 | ✓ | 省体积的主要来源 |
| **P3 可压缩** | 会话记忆 `summary + facts` | ✓ | 已是压缩态，最后手段 |

> **关键修正**：chunks 与 system/query 同级保护。多轮场景下的常规裁剪**只动 P2/P3**，不动 chunks。

### 4.2 额度模型

不是给各部分分固定百分比，而是：

```
总窗口额度 −（system + query + chunks 实际占用） = 剩余额度 → 分配给 history + memory
```

即 **chunks 先按实际占用占位**，剩余额度才分给历史与记忆，天然保证证据不被挤掉。

### 4.3 裁剪顺序（只动 P2/P3）

| 顺序 | 动作 | 说明 |
|---|---|---|
| 1 | **冗余去重**（无损） | memory 已覆盖的旧轮次，不再重复塞 history 原文。纯赚，不丢信息，优先做 |
| 2 | **截取 history** | 默认 6 条 → 2–4 条，保留最近。省体积最多；指代多指向最近几轮，2–4 条基本够 |
| 3 | **压缩 memory** | 再摘要一次 / 截取 `facts` / 丢弃低价值 fact。最后手段 |

> 若 1→3 做完后仍超窗，说明 **chunks 自身太大** → 此时才启用 §5 的 chunks 压缩方案（兜底）。

### 4.4 记忆独立成块（修语义错位）

目标结构——记忆不再混进 `question`：

```
长期记忆:
{memory}

历史对话:
{history}

当前问题:
{query}
```

落地：修改 Nacos `CORE_RAG_TEMPLATE` 增加占位符 + 调整 `generator.py` 装配逻辑。低成本高收益。

### 4.5 冲突仲裁：文档优先

提示词模板中显式声明：

> 当记忆或历史对话中的结论与本次检索到的文档内容冲突时，**以检索到的文档为准**。文档是现行事实，记忆是历史会话摘要。

用于消除"拿 3 轮前的旧版本结论回答，而文档已更新"这类错误。

### 4.6 指代消解

- **短期**：`history` 条数改为可配（新增 `HISTORY_MAX_MESSAGES`，默认 6，可调至 10），当前写死在 `get_history` 默认值里。
- **中期**：在专业咨询链路增加 **query 上下文补全**——用 history + memory 把「它 / 那个方案」补全为独立 query 再检索。复用既有 `query_augmenter`（HyDE / 子查询 / 回溯）做前置补全，可同时提升召回与生成准确性。

### 4.7 记忆质量与时效

- **本侧只管注入环节**。`facts` 的时效标记、记忆 TTL、compaction 触发规则属于生成与存储侧，见持久化方案 §5.5 与架构决策文档 §2.4，本文档不重复设计。
- 已知风险：记忆是模型自生成的摘要，多轮累积会失真；本侧能做的是限制其体积（`MEMORY_MAX_CHARS`）并在模板里声明文档优先（§4.5）。失真本身的治理在生成侧。
- `memory_text` 设长度上限（`MEMORY_MAX_CHARS`），超限再压一次（复用压缩管线）。
- 清理入口已具备：`DELETE /v1/chat/context/{session_id}`（清窗口记忆，不影响历史与会话）。

## 5. chunks 压缩方案（兜底）

> **定位**：仅在 **chunks 自身就使 prompt 超窗**时启用（长文档检索、P0 单独超限）。多轮场景的常规裁剪走 §4.3，不动 chunks。两者是"常规手段 vs 最后手段"的关系。

### 5.1 多级管线（按大小配置）

```
原始 chunks（已 rerank，含 score）
   │
   ├─ L0 截取（按大小，零成本）
   │     ├─ 单片段截短：len(content) > MAX_CHUNK_CHARS 的片段截到该长度（保留 doc_name/page）
   │     └─ 总量截取：按 rerank_score 降序累加，累计达 MAX_TOTAL_CHARS 即停止保留后续片段
   │
   ├─ L1 相关性精选（可选）：score < SIM_THRESHOLD 的低分片段直接丢弃              [零成本]
   │
   └─ L2 LLM 摘要压缩（付费·默认关）：若 L0/L1 后累计仍 > HARD_TOTAL_CHARS，
        对保留片段做摘要/合并（Map-Reduce），输出压缩文本 + 保留溯源引用
```

- **触发条件**：`Σlen(chunk.content) > MAX_TOTAL_CHARS`。
- **单片段上限** `MAX_CHUNK_CHARS`：避免一个超长片段吃掉全部额度。
- **硬上限** `HARD_TOTAL_CHARS`：超过则强制继续截取，或启用 L2 摘要。
- **与模型窗口的关系**：字符数是工程近似（中文约 1 字 ≈ 0.6–1 token，英文约 4 字符 ≈ 1 token），配置上限须按模型上下文窗口**留出生成与系统提示余量**，不要顶格。

### 5.2 数据契约

```python
@dataclass
class CompressResult:
    chunks: list[RetrievedChunk]        # 截取/压缩后保留的片段（L0/L1）或 L2 产出的合成片段
    method: str                         # none | truncate | select | llm_summary
    chars_before: int                   # 压缩前累计字符数
    chars_after: int                    # 压缩后累计字符数
    kept_indices: list[int]             # 保留的原始片段下标（溯源/可解释）
    dropped: int
```

- 返回结构扩展为 `CompressResult`（当前签名返回 `list[RetrievedChunk]`，落地时调整 `router` 调用点与 generator 入参）。

### 5.3 关键流程

```
_compress_context(query, chunks, session_id)
  1. chars_before = sum(len(c.content) for c in chunks)
  2. if chars_before <= MAX_TOTAL_CHARS 且无单片段超限:
         return CompressResult(chunks, 'none', ...)
  3. L0 单片段截短：len(c.content) > MAX_CHUNK_CHARS → 截到 MAX_CHUNK_CHARS
       （附截断标记，保留 doc_name/page）
  4. L0 总量截取：按 rerank_score 降序累加，累计 + 下一个 > MAX_TOTAL_CHARS 则停止保留
  5. L1（可选）：丢弃 score < SIM_THRESHOLD 的片段
  6. if 累计 <= HARD_TOTAL_CHARS: return CompressResult(..., 'truncate'|'select')
  7. L2（若启用）：对保留片段做 LLM 摘要合并 → 合成片段（带 doc_name/page 汇总引用）
  8. except: logger.warning; return CompressResult(原样 chunks, 'none')   # 回退
```

### 5.4 质量保证要点

- **不要按字符硬切**：硬切会切断句子、反而更伤质量。应**按句子边界截断**——复用 `core/rag_indexer/semantic_splitter.py` 已有的 `sentence_split_regex=r'(?<=[。！？\n])'` 逻辑，截到不超过上限的最后一个完整句。
- **超长单片段优先摘要而非截断**：`MAX_CHUNK_CHARS` 触发时，若 L2 开启应走摘要；未开启才截短，并在 `method` 标记 `truncate` 以便监控。
- **截取前先去重**：优先丢"低分**且**与已保留片段高度重复"的（MMR/相似度去重），同样字数下信息量更高。
- **透出 `dropped`**：响应或日志中记录被丢弃片段数，让用户知道回答可能未覆盖全部检索结果，避免静默丢信息。

## 6. 配置（`common/config.py`）

**多轮装配侧**

| 配置项 | 默认 | 说明 |
|---|---|---|
| `HISTORY_MAX_MESSAGES` | `6` | 注入 prompt 的历史消息条数（超限按 §4.3 截取），替代 `get_history` 写死的 `last=6` |
| `MEMORY_MAX_CHARS` | `2000` | 记忆注入文本字符上限，超限再压缩一次 |

**chunks 压缩侧**

| 配置项 | 默认 | 说明 |
|---|---|---|
| `COMPRESS_STRATEGY` | `truncate` | `none`(关闭) / `truncate`(L0 截取) / `select`(L0+L1) / `summary`(含 L2) |
| `COMPRESS_MAX_TOTAL_CHARS` | `8000` | 软上限：累计内容字符数，超过则按分数截取 |
| `COMPRESS_MAX_CHUNK_CHARS` | `1500` | 单片段字符数上限，超出的片段先截短 |
| `COMPRESS_HARD_TOTAL_CHARS` | `16000` | 硬上限：超过强制继续截取，或启用 L2 摘要 |
| `COMPRESS_SIM_THRESHOLD` | `0.3` | L1 相关性丢弃阈值（仅 `select`/`summary` 生效） |
| `COMPRESS_LLM_SUMMARY_ENABLED` | `false` | 是否允许 L2（付费）；false 时超硬上限退化为强制截取 |
| `COMPRESS_MODEL` | 复用 `config.LLM_MODEL_NAME` | L2 摘要所用模型 |

## 7. 可观测性

- **装配侧**：记录 `chunks / history / memory` 三部分各自字符数与占比，监控"谁被裁了、裁了多少"（当前完全黑盒）。
- **压缩侧**：压缩触发率、平均压缩比（`chars_after/chars_before`）、L2 占比、压缩耗时（p95）。
- 日志：进入 L2 或触发 history/memory 裁剪时 `logger.info`（含 `session_id`、`turn_id`、`method`、ratio）——带 `turn_id` 才能让评测结果回溯到具体某一轮。
- **压缩触发率本身是信号**：若大量请求触发 chunks 压缩，说明问题在上游（切片 `PARENT_CHUNK_SIZE`/`CHILD_CHUNK_SIZE` 过大或 `RECALL_K` 过宽），应调索引侧参数，而非靠压缩兜底。

---

## 8. 安全合规

- **溯源不丢**：L2 摘要须保留原始 `doc_name/page` 汇总，禁止凭空生成无引用内容（防幻觉不可追溯）。
- **内容安全**：压缩/截取不改变来源可信度；低质/越权文档不因"被选中"而改变合规判定。
- **可解释**：`dropped` 数量应可查，避免静默丢弃证据。

---

## 9. 容错降级

- L0/L1 与 history/memory 裁剪均为纯本地计算，不会失败。
- L2 依赖 LLM：超时/异常 → 捕获 → 回退到 L0 结果（或原样）+ `logger.warning`，**不抛到主链路**。
- 记忆服务异常时 `memory_text=''`，不注入记忆，不影响主链路（已优雅降级）。
- L2 关闭且超硬上限 → 强制 L0 截取，保证不超上限。

## 10. 质量保证与 RAGAS 接入

**核心认识**：压缩/裁剪本质是"丢信息换窗口与成本"，无法 100% 保证回答能力不降；能保证的是**损失可控、可度量、可回退**。

### 10.1 评测方法

1. **离线评测集**：攒 50–200 条真实问答（带标准答案或关键要点），在"不压缩 / truncate / select / summary"各档下跑，对比关键点命中率。
2. **多轮评测集（必须单独建）**：多轮对话场景，对比"带记忆 / 不带记忆 / 带历史"三档，人工重点看**是否引用了过期的历史结论**。
3. **RAGAS 量化**：`faithfulness`（是否忠于上下文）、`answer_relevancy`、`context_recall`。注意记忆是模型自生成的摘要，本身可能失真，会污染 faithfulness，需单独观测。
4. **回归阈值**：压缩/裁剪后指标相对基线的**降幅 ≤ 2%**，超过则收紧上限或关闭 L2。
5. **灰度**：按租户/会话灰度，结合 RAGAS 审计采样结果验证。

### 10.2 给 RAGAS 留的接入点

本文档不实现评测，只保证评测需要的信号取得到：

| RAGAS 需要 | 取数方式 |
|---|---|
| `question` / `answer` | 由 `router._audit_llm_result`（当前 no-op）在生成结束后透出；也可从已落库的 `rag_turn` 取（持久化方案 §9） |
| `contexts` | **必须取压缩/裁剪后的**——`CompressResult.chunks` 才是模型真正看到的内容；取压缩前的数据会高估 `context_recall`、低估压缩代价 |
| 裁剪元信息 | `CompressResult` 的 `method` / `chars_before` / `chars_after` / `dropped`；以及本次 `history` 条数、`memory` 是否被限长（§7 可观测性要求的埋点） |

- 采样标记落在业务侧 `rag_turn.eval_flag`，指标结果落在评测侧 `rag_eval_run`，业务库不做计算——边界见持久化方案 §9。
- 装配侧与压缩侧的埋点要**带上 `turn_id`**，否则评测结果无法回溯到具体某一轮。

## 12. 风险与开放问题

- **字符数 ≠ token 数**：按字符配置是工程近似，中英文混排偏差较大；上线后需按真实请求校准上限并保留余量。
- **L2 摘要可能丢细节**：建议仅对"超硬上限"的极端场景启用，常规走 L0/L1。
- **记忆失真污染**：记忆是模型自生成的摘要，多轮累积可能失真并污染 faithfulness；需时效性标记与定期校验。
- **指代补全的代价**：query 补全会增加一次 LLM 调用，仅在专业咨询链路、且历史中存在指代词时触发，避免无谓成本。
- **替代路线**：换用长上下文模型（如 128k）可绕开压缩，但成本高；压缩作为降本增效的补充而非唯一手段。
- **与记忆压缩的关系**：`core/session_memory` 的 compaction 是跨轮长期摘要，与本处单轮上下文压缩职责不同，可共用 LLM 摘要能力但互不替代。
